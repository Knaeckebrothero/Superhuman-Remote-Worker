# GLM-5.2 Model Family — Design

**Status:** 📐 Designed, not yet implemented (2026-06-17). Approved scope: **Approach A — core scaffold fork** (deepseek-style).
**Date:** 2026-06-17
**Builds on:** [`docs/superpowers/specs/2026-05-31-config-matrix-db-overrides-design.md`](2026-05-31-config-matrix-db-overrides-design.md) (matrix resolution mechanics), [`docs/design/guardrails_matrix.md`](../../design/guardrails_matrix.md), and the `deepseek` / `minimax-m3` family additions (commits `21b5ce8c`, `d0950927`) as the pattern precedent. Runtime catalog wiring follows the OpenRouter system-provider routing fix (`docs/tests/openrouter_system_provider_routing_verification.md`).

> **TL;DR** — Add a new `glm` model family for Zhipu **GLM-5.2** (text-only, ~1M-context, hybrid-reasoning, served via OpenRouter). GLM-5.2's profile is a near-exact match for the existing `deepseek` family (text-only OpenRouter reasoning model, standard OpenAI tool wire), so we mirror that pattern: a `glm` block in `config/model_config_matrix.yaml`, three forked prompts (worker `systemprompt`, persistent-chat `systemprompt_interactive`, `persona`), an empty `glm.yaml` guardrails file, and — critically — a `glm` branch in **all four** family-detection sites that must stay in sync. Phase prompts (`strategic`/`tactical`/`summarization`/`instructions`) deliberately inherit `default`. Reasoning effort is **not** a matrix setting; it rides on the per-model catalog row.

---

## 1. Motivation & goals

GLM-5.2 (released 2026-06-13) is a 744B-MoE / ~40B-active hybrid reasoning model with a usable 1M-token context window, strong agentic/tool use, and an open MIT release. It is now live on OpenRouter (`z-ai/glm-5.2`). We want it available as a first-class option in both the **worker** (job) path and the **persistent-chat** (session) path, with model-appropriate prompts and inference settings rather than the generic `default` fall-through.

**Goals**

1. A `glm` family that resolves correctly in every code path that maps a model → family (backend, orchestrator, frontend, admin UI).
2. Specialized prompts for the worker and persistent-chat paths plus a GLM identity, encoding GLM-5.2's reasoning-model hygiene and agentic strengths.
3. Inference settings reflecting GLM-5.2's published characteristics (text-only, 1M context, Z.ai default sampling).
4. Mirror the established `deepseek`/`minimax-m3` addition pattern exactly — no parallel machinery.

**Non-goals (explicitly deferred)**

- **Aux-model prompt forks.** GLM is a chat/worker model, *not* the auxiliary/background model (DeepSeek V4 Flash keeps that role), so `memory_extraction` / `memory_assembler` / `curation` are **not** forked.
- **Phase-prompt forks.** `strategic` / `tactical` / `summarization` / `instructions.md` inherit `default` — they are model-agnostic and GLM uses the standard tool wire, so a fork adds maintenance with no benefit (same rationale the `deepseek` block documents).
- **Multimodal / vision.** GLM-5.2 is text-only; vision lives in the separate **GLM-5V-Turbo** model, out of scope here. No `image_tokens` / `pdf_render_dpi` keys.
- **Orchestrator builder matrices** (`orchestrator/config/builder_*_matrix.yaml`) and **per-expert overrides** (`config/experts/*/model_config_matrix.yaml`) — both fall through to `default` and work without a GLM entry. Add later only if GLM needs builder- or expert-specific tuning.
- **Reasoning effort in the matrix.** It is a per-model catalog-row concern (`reasoning_level`), not a family setting (see §3.5).

## 2. Background: how a family is wired today

Adding a family touches more than the YAML. A model ID is mapped to a family in **four** independent places that must agree, plus the matrix/asset files:

| Concern | Site | File |
|---|---|---|
| Backend family resolution (settings-matrix lookup, logging) | `family_of()` | `src/core/model_registry.py:132-190` |
| Orchestrator-side detection (discovery API, admin models form) | regex matcher | `orchestrator/services/family_matcher.py:~67` |
| Frontend family resolution (job/session settings) | `detectModelFamily()` | `cockpit/src/app/views/agent-settings/agent-settings.types.ts:86-118` |
| Admin family-override picker | `FAMILIES` array | `cockpit/src/app/views/admin/config/admin-config.component.ts:40` |

The settings-matrix lookup in `_apply_settings_matrix()` (`src/core/loader.py:556-635`) calls `family_of(model)` directly — so the catalog row's explicit `family` field alone is **not** sufficient; the `family_of()` branch is required for the matrix row to be selected. Recognized `settings` keys (`temperature`, `top_p`, `top_k`, `multimodal`, `parallel_tool_calls`, `model_max_context_tokens`) are written to `config.llm`; `image_tokens`/`pdf_render_dpi` route to `config.limits`; unknown keys are silently ignored. Context limits are derived from `model_max_context_tokens` via fixed fractions: `context_threshold_tokens = base × 0.80` (`CONTEXT_THRESHOLD_FRACTION`, loader.py:43), `message_count_min_tokens = base × 0.40` (`MESSAGE_COUNT_MIN_FRACTION`, loader.py:44).

## 3. Design

### 3.1 Family detection — add `glm` to all four sites

Substring `"glm"` matches every transport form of the ID (`openrouter/z-ai/glm-5.2`, `z-ai/glm-5.2`, bare `glm-5.2`):

- `src/core/model_registry.py` — add `if "glm" in name: return "glm"` alongside the other substring matches in `family_of()` (the 171-188 block).
- `orchestrator/services/family_matcher.py` — add `(re.compile(r"glm", re.IGNORECASE), "glm")` to the rule list.
- `cockpit/src/app/views/agent-settings/agent-settings.types.ts` — add `if (name.includes('glm')) return 'glm';` in `detectModelFamily()`.
- `cockpit/src/app/views/admin/config/admin-config.component.ts` — add `'glm'` to the `FAMILIES` array.

### 3.2 Settings block (`config/model_config_matrix.yaml`)

```yaml
glm:
  prompts:
    systemprompt: systemprompt_glm.txt
    systemprompt_interactive: systemprompt_interactive_glm.txt
    persona: persona_glm.txt
  guardrails:
    file: glm.yaml
  settings:
    temperature: 1.0           # Z.ai published default; no low-temp rec, thinking on by default
    top_p: 0.95                # Z.ai published default
    multimodal: false          # GLM-5.2 is text-only (vision = separate GLM-5V-Turbo)
    parallel_tool_calls: false # brand-new model — start safe, flip to true once validated
    model_max_context_tokens: 1000000   # usable 1M window
```

`strategic`, `tactical`, `summarization`, and `instructions` are intentionally omitted (inherit `default`). Derived limits: threshold = 800,000; message-count-min = 400,000.

### 3.3 The three forked prompts

Each starts from the `default` scaffold + the deepseek reasoning-model pattern, then layers GLM-5.2 specifics. The design intent (exact wording finalized at implementation):

- **`config/prompts/systemprompt_glm.txt`** (worker path):
  - Reasoning-channel hygiene — keep private reasoning in the thinking channel; never emit it in messages, deliverables, or tool arguments (OpenRouter returns reasoning out-of-band).
  - No redundant chain-of-thought scaffolding — the `reasoning_effort` dial owns reasoning depth; instructing "think step by step" in output fights the thinking trace.
  - One tool call per turn — matches `parallel_tool_calls: false` (relax when that flips to `true`).
  - Mild output-density discipline (concise, match length to the task) — calibrated as general reasoning-model hygiene, **not** a GLM-specific verbosity claim (no evidence GLM is as verbose as V4).
- **`config/prompts/systemprompt_interactive_glm.txt`** (persistent-chat path): same hygiene + one-tool-per-turn, in a collaborative live-session tone.
- **`config/prompts/persona_glm.txt`** (identity): operating rules leaning into GLM-5.2's headline strengths — methodical **long-horizon agentic execution** (persist, record blockers, finish the whole task) and **grounding long-context work in specific retrieved passages** (exploit the 1M window; reason from the quoted passage, not a general impression).

### 3.4 Guardrails (`config/guardrails/glm.yaml`)

Starts empty, mirroring `deepseek.yaml`:

```yaml
tool_examples: {}
nudges: {}
```

GLM uses the standard OpenAI tool wire via OpenRouter, so the `default.yaml` tool examples and nudges apply unchanged. Populate later only if real runs show GLM-specific tool-format drift.

### 3.5 Reasoning effort — catalog row, not matrix

Reasoning is configured per-model on the catalog row's `reasoning_level` (`ModelMeta.reasoning_level`, `model_registry.py:59`). For OpenRouter models, `_create_openrouter_llm()` (`loader.py:2838-2958`) passes it as `extra_body["reasoning"] = {"effort": <level>}` when set and not `"none"`; reasoning output is captured by `src/llm/reasoning_chat.py` (`reasoning` / `reasoning_content` / `reasoning_details`). GLM uses the standard `"api"` reasoning method, so `detect_reasoning_method()` (`loader.py:2310-2320`) needs **no change** — but the implementation must **verify GLM is not added to the "none" tuple** (that would suppress the effort param). Operators set `high` (everyday) or `xhigh` (max; OpenRouter maps `xhigh`→max) when creating the `openrouter/z-ai/glm-5.2` rows in Admin → Models, along with the `meta.provider` field per the OpenRouter routing fix.

- `tests/test_settings_matrix.py::TestRealMatrixFamilies`: add `("glm-5.2", 1000000)` and assert derived `context_threshold_tokens == 800000`, `message_count_min_tokens == 400000`, and that `glm` settings resolve (temp 1.0, top_p 0.95, multimodal false, parallel_tool_calls false).
- If `orchestrator/services/family_matcher.py` and the cockpit `detectModelFamily()` have test suites, add matching `glm` cases so all four detectors stay verified in sync.

## 6. Verification

- `pytest tests/test_settings_matrix.py tests/test_model_registry.py` (CI is the gate — local env is Py3.14/dep-noisy).
- Cockpit: `vitest` for the family-detection/types specs.
- YAML load-check of `config/model_config_matrix.yaml`; confirm the three referenced prompt files exist.
- Cross-check that `family_of()` (Python) and `detectModelFamily()` (TS) agree on the `glm` inputs.

## 7. Risks & open items

- **`parallel_tool_calls: false` is a deliberate conservative default** for a 4-day-old model. If GLM proves reliable with parallel calls on OpenRouter, flip to `true` and relax the "one tool call per turn" prompt line.
- **Temperature 1.0 / top_p 0.95** follows Z.ai's published defaults; GLM did not publish a low-temp coding recommendation, and low temp can hurt thinking models. Per-model catalog rows can override if needed.
- **Brand-new model**: benchmarks unpublished at launch; settings may need calibration once real worker/session runs exist.

## 8. Rollout

1. Land the in-scope changes on `develop` (matrix + prompts + guardrails + 4 detectors + tests + README).
2. In Admin → Models, create the catalog row(s): id `openrouter/z-ai/glm-5.2`, `family=glm`, `provider_kind=system` → `provider_ref=openrouter`, `reasoning_level` `high` (everyday) or `xhigh` (max), plus `meta.provider` per the routing fix. Optionally a second `xhigh` "reasoner" row.
3. Verify in-pod that the `glm` family resolves and reasoning effort reaches OpenRouter.
