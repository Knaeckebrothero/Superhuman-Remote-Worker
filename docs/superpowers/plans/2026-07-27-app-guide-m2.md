# App Guide M2 — Runtime Capability Plane Implementation Plan

> **Status (2026-07-27): design complete; implementation not started.**
> M1 is closed and revalidated. This plan turns Phase 2 of
> `docs/features/app_guide_skill.md` into five bounded slices, beginning with
> M2a. It is based on the current tree at `2f88ab47`; implementation must
> re-check named seams before editing because nearby session code is active.

## Goal

Give SRW one bounded, versioned way to answer:

- whether the running product implements a capability;
- whether the deployment enables and can currently support it;
- whether the authenticated caller may use it;
- whether the active session is ready for it; and
- whether the current agent can execute, propose, or only explain the next
  step.

The result is an advisory observation for product explanation. It never
authorizes an operation. The actual operation remains responsible for current
authentication, authorization, resource scope, and runtime preconditions.

M2 is complete only when the managed App Guide can use this observation in a
real persistent session and its claims survive disabled, denied, unattached,
ready, degraded, partial, stale/mixed, and state-change cases without exposing
private configuration.

## Completion boundary

M2 includes:

- a typed capability definition and result contract;
- the first build registry, using capability IDs already reviewed into the
  App Guide;
- a read-only authenticated resolver endpoint;
- a live persistent-session overlay based on the tools and resources that
  actually loaded;
- component-specific declared/unavailable provenance;
- App Guide routing rules for dynamic questions;
- deterministic, integration, model, and live-deployment verification; and
- a dark-launch-to-default-on rollout.

M2 does not include:

- Cockpit help cards, deep links, screenshots, coach marks, or MCP Apps;
- source-repository retrieval;
- a new general feature-flag framework;
- a generic administrator inventory endpoint;
- proactive network probing of every optional provider;
- using a capability snapshot as a permission grant; or
- claiming instant revocation for a local credential-backed operation unless
  that operation or its runtime binding actually revalidates the changed
  state.

Those boundaries keep M2 focused on truthful introspection. Visual help remains
M4, source fallback remains M6, and enforcement gaps discovered by the matrix
must be fixed in the owning operation rather than hidden in the capability
answer.

## Locked implementation choices

| Decision | Choice | Why |
|---|---|---|
| Definition format | A typed Python registry in `src/core/product_capabilities.py` | The current authorities and canonical datasource inventory are Python, both orchestrator and agent ship `src/`, and a framework-free registry is directly importable and testable without adding a parser or a second schema source. |
| Initial IDs | The 18 IDs already present in managed App Guide reference metadata | They have reviewed user guidance and avoid inventing a second taxonomy during implementation. A new ID requires an explicit guide coverage decision. |
| Server boundary | `GET /api/users/me/product-capabilities` in a new router, backed by `orchestrator/services/product_capabilities.py` | New domain behavior should not further grow `orchestrator/main.py`; only router import/include wiring belongs there. |
| Agent boundary | `get_product_capabilities(topic?: str, capability_ids?: list[str])` in a dedicated product-capability tool module | It stays independent of the user-disableable Fleet Management group and independent of the App Guide break-glass switch. |
| Context binding | The model never supplies user, project, thread, repository, or revision | The tool always binds the authenticated user and `ToolContext.thread_id`; the public REST endpoint independently authorizes an optional `thread_id`. |
| Resolution split | Orchestrator resolves build/deployment/user/primary-project facts; the live agent overlays actual tools/backend/attachments/readiness | Neither process is allowed to pretend it observed the other process's live state. |
| Grant scope | With a thread, use its authoritative primary `thread.project_id` exactly as current session grant enforcement does; without a thread use user/global scope only | `/api/users/me/capabilities` currently meets grants across every visible project and is not a session truth source. Secondary mounted projects are resource attachments, not silently added grant scopes. |
| Caching | No application cache in M2; responses use `Cache-Control: private, no-store` | Correctness and revocation behavior matter more than avoiding a small read-only resolution. `registry_revision` still supports later ETag work without changing the schema. |
| Compatibility | Schema `1.0`; breaking shape/enum changes increment major, additive optional fields increment minor | Mixed component deployments are normal. A same-major client ignores unknown fields after projecting onto its allowlisted schema; it never forwards unknown server fields to the model. |
| Failure behavior | Per-layer `unknown`, `completeness=partial`, and bounded error codes | Resolver errors, missing provenance, and stale observations are never re-labelled as intentional disablement or denial. |
| Rollout | Endpoint dark launch, then read-only tool canary, then App Guide dependency and chart default-on | Static M1 guidance remains usable throughout rollout and rollback. |
| Email deployment state | Do not add a synthetic email deployment flag | The current email connector is user-configured and has no deployment flag. A new negative state is valid only if the real create/update/attach/action paths enforce it too. |

### Findings that constrain the design

1. A read-only capability request must not call `_thread_project_ids()` merely
   to learn grant scope because that helper may lazily write back legacy mount
   rows. The resolver admits the thread, uses primary `project_id` for grants,
   and reads any additional attachment facts without mutation.
2. Server and live-agent observations can disagree during an upgrade or
   rebind. Preserve each observation's component and time; the live overlay
   replaces only fields it actually observes.
3. `context.datasources.keys()` is insufficient by itself: a requested email
   attachment may have failed to connect and repository/knowledge attachments
   are represented elsewhere. M2c therefore needs an explicitly redacted
   runtime-facts snapshot populated from the already-authorized attach payload.
4. The capability tool cannot live inside the existing guide-reader
   break-glass return path. Operators may disable damaged guide bytes while
   runtime state reporting remains available.
5. OCI labels are declarations and are not readable from an application
   process by magic. Runtime provenance needs explicit build arguments and
   environment/registration fields; an artifact digest is `unavailable` unless
   the deployment actually supplies a digest.
6. An endpoint result without a live overlay cannot honestly claim current
   agent actionability. Its `session`/`agent_action` fields remain
   `not_applicable` or `unknown` until a trusted observer supplies them.

### Definition model

`CapabilityDefinition` is immutable and contains only public product metadata:

```python
CapabilityDefinition(
    id="datasources.email",
    topics=("datasources", "email"),
    components=CapabilityComponents(
        authority="orchestrator",
        execution="agent",
        presentation="cockpit",
        guidance="guide",
    ),
    visibility="public",
    title_key="datasources.form.optEmail",
    summary="Attach a scoped IMAP/SMTP mailbox.",
    help_topic_id="datasources-email",
    guide_ref="references/datasources-email.md",
    resolver_key="datasource_email",
    public_qualifier_keys=("email.access_tier",),
    open_action_id=None,
    visual_id=None,
)
```

Definitions do not contain raw environment values, credentials, service
addresses, per-user resources, or permission results. Resolver keys select
reviewed server/live logic; they are not arbitrary import paths or expressions.

The registry validates at import/test time:

- dotted lowercase IDs and topic IDs;
- unique capability IDs;
- one supported resolver key per definition;
- valid components and visibility;
- existing primary guide references;
- agreement between a definition and that reference's `capability_ids`;
- allowlisted qualifier keys;
- bounded titles/summaries/IDs; and
- deterministic canonical serialization.

`registry_revision` is `sha256:<hex>` over canonical definition bytes. It
changes for semantic definition/help mapping changes, not for dynamic state.

- `workspace.supports_shell`: boolean.

guide text or localized reason-code presentation.

### State enums

| Field | Values |
|---|---|
| `completeness` | `complete`, `partial` |
| `visibility` | `public`, `conditional`, `hidden` |
| `build.state` | `supported`, `unsupported`, `unknown` |
| `deployment.state` | `enabled`, `disabled`, `degraded`, `unknown` |
| `user.state` | `allowed`, `denied`, `no_opinion`, `not_applicable`, `unknown` |
| `session.state` | `ready`, `not_ready`, `needs_attachment`, `needs_upgrade`, `degraded`, `not_applicable`, `unknown` |
| `agent_action` | `can_execute`, `can_propose`, `can_guide`, `unavailable`, `unknown` |
| `freshness` | `fresh`, `stale`, `unknown` |
| `provenance_status` | `declared`, `verified`, `unavailable` |

`unknown` is a real state, not a fallback spelling of disabled/denied.
`agent_action=unknown` is required for the server-only response because the
orchestrator has not observed the final model-bound toolset.

### Reason-code rules

Reason codes are stable snake-case values, registered by layer and compatible
state. M2a starts with the codes required by the 18 definitions and their
tests, including:

- build: `included_in_build`, `not_in_build`, `build_observation_unavailable`;
- deployment: `feature_enabled`, `feature_disabled`,
  `connector_type_available`, `provider_not_configured`, `service_degraded`,
  `deployment_observation_unavailable`;
- user: `admin_allowed`, `approved_user`, `grant_allowed`, `grant_denied`,
  `no_policy_opinion`, `user_observation_unavailable`;
- session: `thread_not_requested`, `live_agent_observation_required`,
  `tool_loaded`, `tool_not_loaded`, `datasource_attached`,
  `datasource_not_attached`, `datasource_connection_degraded`,
  `workspace_ready`, `workspace_required`, `workspace_not_ready`,
  `knowledge_ready`, `knowledge_unavailable`, `cloud_attached`,
  `cloud_not_attached`, `session_observation_unavailable`; and
- evaluation: `resolver_error`, `stale_observation`, `result_limit`,
  `response_size_limit`, `capability_not_visible`.

M2a's compatibility table rejects impossible pairs, such as
`state=enabled/reason_code=feature_disabled`. Unknown provider-specific
details remain internal and map to one safe code. An exception produces
`unknown`, `completeness=partial`, and a bounded `evaluation_errors` item; it
never produces a negative policy claim.

Each error item contains only:

```json
{
  "code": "resolver_error",
  "capability_id": "datasources.email",
  "layer": "deployment",
  "source_component": "orchestrator",
  "retryable": true
}
```

No exception text, host, provider response, project, datasource, user, or
credential detail crosses the boundary.

### Visibility and filtering

Visibility is evaluated before capability data or errors are serialized:

- `public` definitions may be explained to any approved caller;
- `conditional` definitions appear only when their safe discovery policy
  passes; and
- `hidden` definitions are omitted unless a future explicit discovery policy
  admits them.

A syntactically valid requested ID that is unknown or not visible receives the
same omission and safe `capability_not_visible` request error. The response
does not reveal whether a hidden definition exists. No initial M2 definition is
hidden; the contract is present so later administrator-only features do not
force a breaking change.

`topic` and repeated `capability_id` filters are exact registry tokens, not
model free text. When both are supplied they intersect. Results are sorted by
capability ID before applying `limit`.

### Endpoint contract

```text
GET /api/users/me/product-capabilities
    ?thread_id=<uuid>
    &topic=<exact-topic-id>
    &capability_id=<exact-id>
    &capability_id=<exact-id>
    &limit=<1..50>
```

- `thread_id` is optional. When absent, `scope.kind=user`,
  `session.state=not_applicable`, and `agent_action=unknown`.
- A supplied thread goes through `require_thread_owner` before its row or
  resource state is used.
- `topic` is at most 80 characters.
- At most 20 explicit capability IDs are accepted.
- `limit` defaults to 20 and is capped at 50.
- The encoded response is capped at 64 KiB. Deterministic tail truncation sets
  `truncated=true`, `completeness=partial`, and a bounded size/limit error.
- There is no cursor in M2. Callers use an exact topic/ID filter rather than
  sweeping an unbounded registry.
- Responses set `Cache-Control: private, no-store`.
- The endpoint is read-only and must not run mount backfills, provision
  resources, connect datasources, start browsers, or mutate health state.

Authentication selects the user. The admitted thread selects the primary
project scope. Query parameters never select another user or arbitrary project.

### Live agent overlay

The agent tool:

1. validates its topic and at most 12 capability IDs;
2. calls the endpoint with `ToolContext.thread_id`, never a model-provided
   thread;
3. validates schema major and projects the response onto fields known to the
   client;
4. overlays a fresh `SessionRuntimeFacts` snapshot;
5. derives `agent_action` from the final loaded tools and non-actionable layer
   states;
6. revalidates the final result model and 32 KiB tool-output limit; and
7. returns structured JSON containing a concise deterministic summary field
   for text-only consumers.

`SessionRuntimeFacts` contains only:

- observation time;
- current backend ID and public backend feature booleans;
- aggregate attached datasource type IDs;
- aggregate effective email tier, if any;
- whether a requested attachment failed to create a live connection;
- knowledge-store/binding availability;
- cloud mount/protected-overlay booleans; and
- the exact post-instantiation tool-name set.

It contains no datasource names or IDs, accounts, folders/tags, credentials,
connection strings, repository names, project IDs, mount paths, workspace
addresses, or user content.

The snapshot is rebuilt at attach and refreshed after datasource/backend/tool
rebinds. The tool reads it atomically; it does not inspect mutable raw attach
payloads during a model call.

The overlay updates only facts it can prove:

- configured-but-not-instantiated tool names never become `ready`;
- an authorized email attachment with no live connection/tools becomes
  `degraded`, not `needs_attachment`;
- no email attachment becomes `needs_attachment`;
- `datasources.email.send` is ready only when the live tier and final
  `email_send` tool agree;
- backend support comes from the active backend object, not its requested
  config alone; and
- `can_execute` requires the exact operation tool, while `can_propose` requires
  a real proposal/approval path.

If the orchestrator request fails, the tool reports a bounded partial/unknown
result. It does not manufacture build/user facts from local state. The managed
guide remains usable for stable how-to guidance and must state that current
availability could not be checked.

### Precedence and actionability

Resolution narrows monotonically:

1. registry/build;
2. deployment configuration and safe health observations;
3. authenticated user plus primary project grants/policy;
4. admitted thread and live-agent session observations; then
5. agent actionability.

A later layer cannot make an unsupported build supported, bypass a disabled
deployment gate, or widen a denied grant. A later fresh observer may replace an
earlier `unknown` session observation with a proven state.

`agent_action` means:

- `can_execute`: the final toolset contains the reviewed direct operation;
- `can_propose`: the final toolset contains the reviewed dry-run/proposal or
  approval-gated operation;
- `can_guide`: the agent can explain the reviewed user path but has no direct
  operation;
- `unavailable`: neither a direct/proposal action nor reviewed guidance is
  available; or
- `unknown`: final actionability was not observed.

It does not mean the action will succeed. The agent must call the operation,
which then applies its own current enforcement.

## Security and privacy invariants

1. Capability output is never accepted as an authorization credential or
   passed into an operation as proof.
2. Every thread-scoped observation follows normal admission before resource
   inspection. A forwarded internal user header is transport context, not
   permission to name a different thread.
3. The model cannot select identity, grant scope, repository, revision, raw
   resolver, provider, or service address.
4. Visibility filtering happens before state/error emission.
5. Resolver failures are fail-closed for positive claims but are reported as
   unknown, not as a fabricated denial.
6. Only registry-declared qualifier keys and bounded values are serializable.
7. No endpoint/tool payload contains credentials, credential-presence details,
   datasource/resource names or IDs, email addresses, mailbox folders/tags,
   repository names, private routes, pod/VM addresses, mount paths, or raw
   exceptions.
8. The read path does not provision, probe with user credentials, backfill,
   start, attach, or mutate anything.
9. Same-major clients drop unknown fields before model exposure. An unsupported
   major version becomes an honest partial/unknown result.
10. Logs and metrics use capability ID, layer/state/reason, completeness,
    latency, and component only. They omit user/thread/project/resource
    identifiers and qualifier values.
11. The real action is the final policy enforcement point. If a test proves an
    operation can continue after a state it promises to recheck was revoked,
    fix that operation or its binding lifecycle before claiming M2 coverage.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Registry becomes a second implementation truth | Definitions contain public metadata and resolver keys only; each layer composes the actual authority seam and coverage tests name it. |
| A broad grants endpoint reports the wrong project result | Thread-bound service resolves the primary project used by current session enforcement; no-thread resolution never meets every visible project. |
| Configured tools are mistaken for instantiated tools | Actionability uses the final post-load name set and a redacted runtime-facts snapshot refreshed on every rebind. |
| Mixed agent/orchestrator versions break parsing | Major/minor contract, bounded projection of same-major fields, unsupported-major degradation, and component provenance. |
| Hidden capabilities leak through errors/counts | Visibility precedes resolution/serialization; unknown and hidden explicit IDs share one response; counts apply only after visibility. |
| Qualifiers become a secret side channel | Registry allowlist, scalar/token-only types, tight lengths/counts, and redaction tests with realistic datasource payloads. |
| Read-only lookup mutates lazy state | The service avoids mutating backfill/provision helpers; tests assert no write/provision/start calls. |
| Snapshot is treated as permission | Tool/guide language, no authorization token, trajectory tests, and changed-state-before-action tests. |
| A local datasource grant is revoked mid-session but the bound tool survives | M2 claims only the refresh/recheck behavior proven by the owning binding/action. Any mismatch is an enforcement bug to fix before that capability can pass acceptance. |
| Provenance claims are stronger than evidence | `declared`, `verified`, and `unavailable` remain distinct; tags/short SHAs are never called immutable revisions or digests. |
| M2 grows into every product domain at once | Contract first, email vertical slice second, then resolver adapters for the remaining 18 definitions using the same tests and no schema forks. |

## Definition of done

M2 is done when:

1. all 18 initial IDs have one validated definition and primary guide mapping;
2. the endpoint is authenticated, owner/project scoped, bounded, read-only,
   visibility-safe, and no-store;
3. the live tool is present on every user-facing persistent tier and records
   actual post-load tools;
4. server-only and live-agent observations remain distinguishable;
5. email and a truly deployment-gated capability pass the complete state
   matrix;
6. capability output contains no private resource/configuration data;
7. component provenance is declared/unavailable/mixed rather than flattened;
8. guide answers use runtime state for dynamic claims and preserve unknown;
9. changed state is enforced by the real operation/binding rather than a
   stale snapshot; and
10. focused, full-union, model, live, Ruff, Helm, and diff gates are green with
    zero critical false-positive claims.
