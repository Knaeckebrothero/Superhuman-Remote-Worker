# Cockpit Internationalization (EN / DE)

Per-user language setting for the Cockpit UI, driven by `users.settings.language`. English remains the default and source-of-truth language; German is the first additional locale. Only UI chrome is translated — agent outputs, chat content, job descriptions, and user-authored text stay in whatever language the user wrote them in.

## Problem

The Cockpit only ships English strings today. Customer base is mixed EN/DE and the German cohort consistently asks for a native UI. A global compile-time build per locale (`@angular/localize`) would force either a full reload on switch or locale-specific deployments — neither matches "user flips a setting and the UI updates." We need a runtime solution wired to the existing per-user settings infrastructure.

## Scope

**In scope**
- All static UI strings in the cockpit (labels, buttons, menu items, tooltips, toasts, validation messages, empty states, confirmation dialogs)
- Date/number/currency formatting via Angular's built-in pipes with a synchronized `LOCALE_ID`
- Keycloak login UI locale (pass `ui_locales` hint on redirect)
- Per-user language preference stored in `users.settings.language`, default = browser locale, fallback = `en`
- SSR-rendered strings (translations loaded on server before first render)

**Out of scope (v1)**
- Agent-generated content, chat messages, job outputs, project files
- Admin-only debug surfaces (`cockpit/src/app/debug/**`) — ship in EN only
- RTL layouts (not needed for EN/DE)
- Backend error messages returned by the orchestrator API (English only; cockpit maps known error codes to translated messages)
- Email templates (separate concern, handled orchestrator-side)

## Library Decision: `@jsverse/transloco`

| Option | Verdict | Why |
|--------|---------|-----|
| `@angular/localize` (compile-time) | ❌ | Forces full reload on language change or separate deployments per locale. Doesn't fit settings-driven switch. |
| `@ngx-translate/core` | ❌ | Mature but API predates signals/standalone; not actively modernized. |
| `@jsverse/transloco` | ✅ | Runtime switch without reload, ~8kB gzipped, first-class signals + standalone support, typed keys, built-in lazy-loading of translation chunks, active maintenance. Successor to `@ngneat/transloco`. |

## Architecture

### Storage

Add `language: "en" | "de-DE"` to the `UserSettings` interface in `cockpit/src/app/core/models/api.model.ts`. No schema migration needed — `users.settings` is JSONB (`orchestrator/database/schema.sql:92-96`) and the existing `PATCH /api/settings/preferences` endpoint already accepts arbitrary keys.

### Resolution order (on bootstrap)

1. `users.settings.language` if set
2. `navigator.language` → `navigator.languages` matched against supported locales
3. `en`

On the server (SSR), the settings service runs before hydration and sets transloco's active language before the first render. Unauthenticated flows (login page, public error pages) use the browser-locale fallback only.

### Data flow

```
Bootstrap → SettingsService.loadPreferences()
         → TranslocoService.setActiveLang(resolved)
         → LOCALE_ID updated (for DatePipe/DecimalPipe/CurrencyPipe)
         → KeycloakService receives ui_locales hint on next redirect
User flips selector → SettingsService.updatePreferences({language: 'de'})
                    → TranslocoService.setActiveLang('de') (instant)
                    → LOCALE_ID updated via signal → pipes re-render
```

No page reload. No route change.

### File layout

```
cockpit/src/assets/i18n/
  en.json           # source-of-truth, feature-grouped keys
  de-DE.json        # mirrored structure, translated values
```

Feature-grouped keys (not flat):

```json
{
  "common": { "save": "Save", "cancel": "Cancel", ... },
  "nav": { "jobs": "Jobs", "sessions": "Sessions", ... },
  "jobs": { "create": { "title": "New Job", ... }, ... },
  "settings": { ... }
}
```

Lazy-load per feature module only if bundle size becomes a problem — at two locales of ~30KB each, not worth the complexity up front.

## Implementation Plan

### Phase 1 — Foundation (1–2 days)

Goal: everything wired, zero strings migrated yet, app still fully English.

1. `ng add @jsverse/transloco` in `cockpit/` — scaffolds config, `transloco.config.ts`, provider, loader.
2. Configure supported languages: `['en', 'de-DE']`, default `en`, fallback `en`.
3. Create `cockpit/src/assets/i18n/en.json` and `de-DE.json` with empty `{}`.
4. Wire `TranslocoService.setActiveLang` into `APP_INITIALIZER` after `KeycloakService.init()`, reading `SettingsService.preferences().language` once loaded (with browser-locale fallback before auth completes).
5. Add `language` to `UserSettings` interface (`cockpit/src/app/core/models/api.model.ts:211`).
6. Verify SSR path: translation JSON must be readable server-side. Use transloco's `HttpLoader` with Angular's `TransferState` so SSR fetches once and hydrates without refetch.
7. Wire active language into Angular's formatting pipes. `LOCALE_ID` is resolved once at bootstrap and cannot be changed at runtime (long-standing Angular issue #15039), so Angular's built-in `DatePipe`/`CurrencyPipe`/`DecimalPipe` cannot reactively follow a runtime language switch via DI. Two options:
   - **Preferred**: install `@jsverse/transloco-locale` — the official formatting addon ships reactive `translocoDate`, `translocoCurrency`, `translocoDecimal`, `translocoPercent` pipes that track transloco's active language out of the box.
   - **Fallback** (if the addon has issues on Angular 21): expose `activeLang` as a signal mirroring `TranslocoService.getActiveLang()`, then pass it as the explicit `locale` argument to Angular's built-in pipes (`{{ date | date:'mediumDate':undefined:activeLang() }}`). Optionally wrap in `LocalizedDatePipe` / `LocalizedCurrencyPipe` so callers don't thread the arg every time.

   Register German locale data at bootstrap: `registerLocaleData(localeDe, 'de-DE')` in `app.config.ts`.
8. Add unit test: bootstrapping with `{language: 'de-DE'}` in preferences sets active lang to `de-DE`.

**Deliverable:** infrastructure ready, `@@@` prefix on any `translate` pipe still renders original English (no strings migrated yet).

### Phase 2 — Language Selector + String Migration (3–5 days)

Goal: German user can switch to German and see a German UI for the most-used surfaces.

1. Add language selector to the Settings page (`cockpit/src/app/pages/settings/settings.component.ts`). Simple two-option toggle or dropdown. Writes via `SettingsService.updatePreferences({language})`.
2. Migrate strings in priority order (each step is shippable independently):
   1. **Navigation + shell** — `layout/sidebar`, `layout/header`, route titles, the `simple/` mobile shell tabs
   2. **Settings page itself** — the page the user just used to switch languages should be fully translated
   3. **Jobs surface** — list, detail, create wizard (high-traffic)
   4. **Sessions surface** — persistent chat, session list
   5. **Projects, datasources, tools** — lower-traffic config surfaces
   6. **Toasts + validation messages** — cross-cutting; migrate last so the `core/components/toast` refactor happens once
3. Convention: use the `transloco` pipe in templates (`{{ 'jobs.create.title' | transloco }}`) and `TranslocoService.translate()` in TS code. No inline English fallbacks — missing keys show the key path, which is loud enough to catch in review.
4. Enable transloco's strict-typing plugin so `translate('jobs.xxx')` fails the build when `xxx` doesn't exist in `en.json`. **Deferred** — not blocking the migration; revisit after all components are translated.
5. German translation: Claude writes the initial translations directly — most strings are short UI labels (buttons, menu items, validation messages) and don't warrant DeepL round-trips. Testers catch quality issues during QA. Parity between `en.json` and `de-DE.json` is enforced by `cockpit/scripts/check-i18n-parity.mjs`, wired into the `test-cockpit` CI job via `npm run i18n:check`. Runs in both `.github/workflows/main.yml` and `.github/workflows/develop.yml`; fails the build on missing, extra, or type-mismatched keys. A local git `pre-commit` hook was considered but not added — no husky infra in the repo, and CI catches drift on every PR.

### Phase 3 — Formatting, Keycloak, Polish (1–2 days)

1. **Formatting audit — done.** Two `| date:'short'` pipe usages in `simple/pages/sessions` and `simple/pages/shell` swapped to `translocoDate` (reactive to language switch). TS helpers using `toLocaleDateString(undefined, …)` / `toLocaleTimeString(undefined, …)` now thread `this.transloco.getActiveLang()` as the explicit locale, so they follow the user's cockpit language instead of the browser default. Covered: `settings`, `agent-list`, `job-list`, `todo-list`, `job-review`, `chat-history`, `inbox-page`, `project-detail`. Admin-only surfaces under `debug/` and the `statistics` dashboard are out of scope per the "admin stays in English" decision. `registerLocaleData(localeDe, 'de-DE')` is wired in `app.config.ts`.
2. **Keycloak `ui_locales` — done.** `KeycloakService.login()` and `.logout()` now pass `locale: 'en' | 'de'` computed from `TranslocoService.getActiveLang()`. Keycloak ships both locales out of the box — the SSO screen matches the cockpit language on first login.
3. **Error-code mapping — done.** New `ErrorMessageService` (`core/services/error-message.service.ts`) resolves an HTTP or runtime error into a translated message with this order: (1) structured `error.code` under `errors.code.<code>`, (2) HTTP status under `errors.http.<status>` / `errors.http.{4xx,5xx,timeout,network}`, (3) caller-supplied fallback key (e.g. `errors.jobs.createFailed`), (4) raw `error.detail` (English, as emitted by the server), (5) `errors.unknown`. The orchestrator currently emits ad-hoc English `detail` strings with no structured codes — the `errors.code.*` bucket is an extension point, pre-seeded with `job.not_found`, `agent.unavailable`, `agent.offline`, `project.not_found`, `permission.denied` so the contract is ready when the server adopts codes. All toast-producing catches in `api.service.ts` (15 call sites) and the ad-hoc `e?.error?.detail || '…'` calls in `simple/pages/sessions` and `simple/pages/chat` now go through the service.
4. QA pass: switch to DE, walk every primary flow (create job, view session, open settings, trigger an error toast), screenshot both locales side-by-side.

### Phase 4 — Maintenance Path

1. **Hardcoded-string check — done.** `cockpit/scripts/check-i18n-hardcoded.mjs` scans `src/app/**/*.{ts,html}` and flags these high-signal patterns:
   - `toast.{error,success,show,warning,info}('literal', …)` — untranslated toast copy
   - `alert('literal')` / `confirm('literal')` / `prompt('literal')` — untranslated native dialogs
   Allowlisted paths (admin / non-user-facing): `src/app/debug/**`, `src/app/shared/components/statistics/**`, `*.spec.ts`, `test-setup.ts`. Escape hatch: add `// i18n-exempt` (or `<!-- i18n-exempt -->` in templates) on the offending line. Template text-between-tags and attribute literals are deliberately *not* scanned — too noisy against Angular bindings and icon spans; the transloco pipe convention plus code review catches those.  Run: `npm run i18n:check:hardcoded`, or `npm run i18n:check` to chain the parity check as well. CI already invokes the combined script in `develop.yml` and `main.yml`.
2. **Translation-key convention — done.** `cockpit/README.md` now has an "Internationalization (i18n)" section covering locale file locations, how to reference keys (pipe in templates, `TranslocoService` / `ErrorMessageService` in TS), the feature-grouped + verb-noun + past-tense naming convention, the `errors.code.*` / `errors.http.*` / `errors.<feature>.<action>Failed` error namespacing, the admin-stays-in-EN rule, and how to run / silence the CI checks.
3. Future-proofing for more locales: the only file that hardcodes the supported list is `transloco.config.ts`. Adding FR/ES later = add to config + add JSON file.

## Risks

| Risk | Mitigation |
|------|------------|
| SSR hydration mismatch if server and client pick different locales | Settings loaded in server's `APP_INITIALIZER`; transferred via `TransferState`. Covered by a Playwright test that renders SSR in DE and asserts no hydration warning. |
| Bundle bloat from eager-loading all languages | Two locales = negligible. If we add 3+, switch to `HttpLoader` per-lang (already the default). |
| Untranslated keys leaking to production | CI parity check (`npm run i18n:check` in `test-cockpit`) fails the build if `de-DE.json` drifts from `en.json`. Strict-typing plugin (deferred) will additionally surface missing keys as build errors. |
| User sets DE then token expires, re-login loses preference | Preference lives in DB, not just in-app state — re-fetched on every login. |
| Translation quality drift over time | Keep `en.json` as the authoritative source (developers write EN, DE is always translated from it). Never edit `de-DE.json` directly without the corresponding `en.json` change. |

## Decisions

- **Translation authoring:** Claude translates initial strings directly — most are short UI labels (buttons, menus, validation). Testers catch quality issues during QA. No external translator or DeepL round-trip for v1.
- **Region vs language tag:** `de-DE` (explicit, BCP 47 convention in most production apps). `de-AT` / `de-CH` variants can be added later without renaming. Default English stays as plain `en` — it's the source-of-truth and doesn't need a region yet.
- **Admin / debug surfaces:** Leave in English permanently for v1. Not customer-facing.
- **Brand names stay untranslated:** Third-party provider labels (OpenAI, Anthropic, OpenRouter, Groq, Codex, Tavily, Google, etc.) are trademarks, not UI copy — render them as-is in both locales. Translate surrounding UI chrome (section headers, hints, labels) but keep the brand token verbatim.
- **Language picker options render in their own language:** The language selector shows "English" and "Deutsch" regardless of the active locale — standard convention so a user who accidentally switched to a language they don't read can still find their way back.
- **Parity enforcement:** Ship-gated in CI (`npm run i18n:check`), not a local git hook. No husky / pre-commit infra added to the repo for this.
