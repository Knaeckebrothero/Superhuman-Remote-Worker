## 1. LangGraph Platform / Agent Server — how the vendor ships this exact architecture

The doc's claim "this is LangGraph's native serverless shape" is **confirmed in detail** by the [Agent Server architecture docs](https://docs.langchain.com/langsmith/agent-server):

- **Two container roles**: API servers "handle client requests (creating runs, reading thread state, streaming results) but do not execute agent code"; **queue workers** "listen to the durable task queue, execute your graph code, and write checkpoints". They scale independently (API on request volume, workers on pending-run count).
- **Postgres is the queue + state store**: "a client sends a request to an API server, which creates a pending run in the durable task queue" (Postgres). Redis is used only for **signaling and streaming pub/sub**; "no user or run data persists in Redis. Run data itself is always read from and written to PostgreSQL."
- **Leasing**: a queue worker "picks up the run, **acquires a lease** on it, loads the appropriate graph, and begins execution." Fairness/exactly-once wording: workers "share the queued runs fairly, without ever executing the same run more than once."
- **Serialization per thread**: "the queue enforces that **at most 1 run can be executed for a given thread at one time**." This is the vendor's version of the doc's turn/batch lease.
- **Concurrency per worker**: `N_JOBS_PER_WORKER` (default 10) concurrent runs per worker process; per-run pool share = `LANGGRAPH_POSTGRES_POOL_MAX_SIZE // N_JOBS_PER_WORKER` ([env-var docs](https://docs.langchain.com/langsmith/env-var-cloud)). `BG_JOB_ISOLATED_LOOPS=true` runs each background worker in its own thread + own PG pool when graph code contains sync work. `BG_JOB_SHUTDOWN_TIMEOUT` (default **180 s**) = drain window on shutdown.
- **Crash recovery**: on retriable failure (transient DB error, shutdown cancellation) the run "is placed back in the queue and **resumed from the last checkpointed step**"; bounded by a max-retries setting. Checkpoints mean "if a worker is interrupted, the run can resume from the last checkpoint rather than from the beginning."
- **Streaming from queue-backed runs**: workers broadcast events to Redis pub/sub; API servers subscribe and forward as SSE. So even the vendor **never streams pod→client directly** — there is always a journal/broker hop. `client.runs.join_stream(thread_id, run_id)` attaches to an active run but "output is **not buffered**, so any output produced before joining will not be received." Thread-level streams (`client.threads.join_stream`) are the durable option: reconnect with the **`Last-Event-ID` header** to resume without loss, or `"-"` to replay from the start; modes `run_modes`/`lifecycle`/`state_update` ([streaming API docs](https://docs.langchain.com/langsmith/streaming)). A `stream_resumable` flag on run creation makes the run's event log replayable; non-resumable events "are consumed and cannot be replayed."
- **Run stream modes**: `values`, `updates` (default), `messages-tuple`, `events`, `debug`, `custom`; multiple modes per request return `(mode, chunk)` tuples.
- **Double texting** ([docs](https://docs.langchain.com/langgraph-platform/double-texting)) is **Platform-only — "not available in the open-source LangGraph framework"**. Four per-run strategies: **reject** (409 the second run), **enqueue** (default; second run waits, runs sequentially), **interrupt** (halt current run, keep its progress as checkpointed state, insert new input, continue), **rollback** (halt AND delete the first run from the DB; new input starts from prior state). Documented caveat on interrupt: graphs must handle "tool calls were initiated but incomplete at interruption, potentially requiring handling or removing partial tool calls."
- **Checkpoint TTL** ([configure-ttl docs](https://docs.langchain.com/langsmith/configure-ttl)): `langgraph.json` → `checkpointer.ttl = {strategy: "delete", sweep_interval_minutes (default 5), default_ttl (minutes)}`. TTL clock **resets on any thread activity** (new run/checkpoint); a background sweeper deletes threads whose expiry passed, so deletion lands between expiry and next sweep. Known wart: `threads.search()` can return TTL-deleted threads (eventual consistency, [issue #6686](https://github.com/langchain-ai/langgraph/issues/6686)).

**Net**: the platform's architecture IS the doc's proposal (Postgres run queue, worker lease, ≤1 run/thread, resume-from-checkpoint on crash, journal-mediated streaming). The one component OSS gives you nothing for is the lease/queue itself — see §5.1.

## 2. AsyncPostgresSaver in production

### 2.1 Versions, serde, security — repo pins are a liability
- Latest `langgraph-checkpoint-postgres` = **3.1.1 (2026-07-30)**. Repo pins `>=1.0.0`.
- **CVE-2025-64439**: before `langgraph-checkpoint` 3.0, `JsonPlusSerializer` had an RCE when deserializing payloads stored in `"json"` mode (the fallback path used when msgpack failed, e.g. on illegal Unicode surrogates). 3.0 removed the pickle/json fallback and added a **constructor allow-list**; the PyPI page now instructs: set **`LANGGRAPH_STRICT_MSGPACK=true`** or pass `allowed_msgpack_modules` "preventing code execution if the database is compromised" ([PyPI](https://pypi.org/project/langgraph-checkpoint-postgres/), [CVE writeup](https://corgea.com/advisories/vulnerabilities/CVE-2025-64439)). In a stateless design the checkpoint DB becomes the *only* state carrier — this hardening is no longer optional.
- Serde protocol changed `tuple[str, str]` → `tuple[str, bytes]` across the 1.x→3.x checkpoint line; **cross-version resume of old checkpoints breaks** in documented ways: missing `channel_values` key on legacy checkpoints ([#6137](https://github.com/langchain-ai/langgraph/issues/6137)), schema/column errors after upgrading the saver ([#3557](https://github.com/langchain-ai/langgraph/issues/3557)). A long-paused job resumed after an image upgrade is the risk shape. Pin exact versions; treat checkpoint-library bumps like DB migrations.
- [Issue #7714](https://github.com/langchain-ai/langgraph/issues/7714) claims **85% storage bloat + 37.8% token overhead** from default checkpoint message serialization with "no opt-out path" — contested but worth knowing when sizing.

### 2.2 Connections: pool + retry, not per-job connections
- Community/production consensus (per search results incl. [k8s deploy writeup](https://medium.com/@yuxiaojian/how-to-deploy-langgraph-agents-to-kubernetes-b3216d0cc961), [forum pooling thread](https://forum.langchain.com/t/langgraph-production-connection-pooling-inquiry/1730)): one **process-wide `AsyncConnectionPool`** (kwargs `autocommit=True, prepare_threshold=0`), `AsyncPostgresSaver(pool)`; behind >a-handful of replicas put **PgBouncer in transaction mode** (which is exactly why `prepare_threshold=0` matters). The saver accepts `Connection | Pipeline | ConnectionPool`.
- **No built-in resilience**: "connections in the pool may become invalid/stale and ... There is no resiliency in this class today" — the working pattern (posted in [#5675](https://github.com/langchain-ai/langgraph/issues/5675) and the forum thread) is a **subclass wrapping every op in retry** on connection-error patterns ("SSL connection has been closed unexpectedly", "connection reset", pool exhausted...), acquiring per-call from the shared pool. Directly relevant: our per-job single `AsyncConnection` (`src/agent.py:1279`) is the fragile variant of this — one dropped TCP connection mid-batch = job failure today.
- **Avoid `pipeline=True`**: [#5675](https://github.com/langchain-ai/langgraph/issues/5675) documents `psycopg.AsyncPipeline [BAD]` / SSL-closed failures esp. behind Supabase/pgbouncer-style poolers; a comment also ties failures to **large state → large per-step INSERTs**.
- `setup()` is idempotent versioned DDL (internal migrations table). Tiendanube's production writeup ([scaling the Postgres checkpointer](https://tadeodonegana.com/posts/scaling-langgraph-postgres-checkpointer/)) instead runs the DDL via **Alembic in CI** and pins/monitors upstream `base.py` for migration drift — matches our "migrations at orchestrator startup, not app-runtime DDL" convention.

### 2.3 Growth and pruning — the real operational cost
- Tiendanube numbers: **~93 rows across the 4 checkpointer tables per 2-message/3-tool-call conversation**; staging hit 56 MB / 18k rows in `checkpoint_blobs` in a week; 120k conversations/week in prod. Mitigations they shipped: checkpoint **only the supervisor graph** (not subgraphs), **partition by `thread_id` (pg_partman)** for cheap deletes, weekly ETL to S3, TTL deletes.
- `checkpoint_blobs` stores every state key's value at every version (write-amplification by design); large artifacts in state → TOAST bloat, WAL spikes, replication lag ([azguards bloat writeup](https://azguards.com/distributed-systems/the-checkpoint-bloat-mitigating-write-amplification-in-langgraph-postgres-savers/)). Keep files/URLs out of graph state.
- Pruning primitives: `delete_thread`/`adelete_thread` remove a thread from `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` (we already delete on terminal per the doc); **`ShallowPostgresSaver`/`AsyncShallowPostgresSaver`** keep only the latest checkpoint per thread — history/time-travel gone, but batch-resume only needs the latest checkpoint, so this is a legitimate blobs-bloat killer for the worker lane ([reference index](https://reference.langchain.com/python/langgraph.checkpoint.postgres)).

## 3. Driving the graph in bounded slices

### 3.1 astream-and-break — the clean mechanism
`astream(..., stream_mode="updates"|"values")` yields **once per superstep**; the consumer drives the loop, so counting yields and `break`ing bounds the run at a superstep edge. Verified against installed langgraph 1.0.5 source (`langgraph/pregel/_loop.py`): `AsyncPregelLoop.__aexit__` unwinds an `AsyncExitStack` that owns the background checkpoint-write futures (`_checkpointer_put_after_previous`), and the code explicitly notes on cancellation it bubbles the exit task "to permit the API consumer to **await it before e.g., reusing the DB connection**". I.e. closing the generator (what `break` does via `aclose()`) flushes pending `durability="async"` checkpoint writes before returning. Resume later with `ainvoke(None, config)` / astream again — standard resume-from-latest-checkpoint. Caveat from [#5682](https://github.com/langchain-ai/langgraph/issues/5682): cancellation may not propagate into **subgraphs invoked via bare `ainvoke` inside a node** (our graph doesn't nest subgraphs; noting for completeness).

### 3.2 recursion_limit / GraphRecursionError — usable but error-shaped
- `recursion_limit` counts **supersteps** ("nodes that run in parallel are part of the same super-step"); standalone config key, NOT under `configurable`; per-run (`graph.invoke(inputs, config={"recursion_limit": N})`) or default via `.with_config()`. **Default changed from 25 → 1000 in langgraph 1.0.6** — we're on 1.0.5 with an explicit 1000000, so unaffected, but a bump crossing 1.0.6 changes behavior for anyone relying on the default. Step counter readable at `config["metadata"]["langgraph_step"]`; `RemainingSteps` managed value enables **graceful in-graph handling before the limit** ([graph-api docs](https://docs.langchain.com/oss/python/langgraph/graph-api)).
- On `GraphRecursionError` with a checkpointer, state at the last completed superstep is persisted and resumable — but it's an exception, indistinguishable at the call site from a genuine runaway loop, and it aborts the in-flight superstep. Fine as a **backstop**, wrong as the batch edge.

### 3.3 interrupt_before/after and interrupt()
- Static breakpoints settable **at compile time or per-invoke** (`graph.invoke(inputs, interrupt_before=["node_a"], config=config)`); resume = `invoke(None, config)`. Per-invoke `interrupt_before=["handle_transition"]` would be a zero-code phase-boundary batch edge — but it's node-name-granular, not count-granular, so it can't express "N supersteps".
- Dynamic `interrupt()` resume semantics — the sharp edge: "**the node restarts from the beginning of the node** where the `interrupt()` was called when resumed, so any code before the `interrupt()` runs again." Side effects before an interrupt must be idempotent. `Command(resume=...)` is **only** for interrupt resumes; passing any `Command` as input "resumes from the latest checkpoint ... the graph will appear stuck if it already finished" — new turns must be plain dict inputs. Multiple parallel interrupts resume via `Command(resume={interrupt_id: value})`.

### 3.4 Durability modes and crash windows
`durability=` on invoke/stream since **langgraph 0.6.0** (replaced `checkpoint_during`; `True`→`"async"`, `False`→`"exit"`) ([Durability reference](https://reference.langchain.com/python/langgraph/types/Durability)):
- `"sync"` — persisted before next step starts. Crash window ≈ 0 supersteps.
- `"async"` (**default**, also the Platform default) — persisted while next step executes; "small risk that LangGraph does not write checkpoints if the process crashes during execution" → crash window ≈ 1 superstep.
- `"exit"` — only at graph exit; a killed pod loses the whole slice. **Incompatible with the stateless design** for workers.
- `pending_writes`: when a node in a superstep fails, writes from **successfully completed sibling nodes are stored** (`put_writes`) and "when you resume graph execution from that super-step you don't re-run the successful nodes" — bounds replay duplication to the failed node ([checkpointer docs](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)).

## 4. Compile-once, invoke-many
- Compiled graphs are **thread-safe and stateless**: "entirely safe to share between executions, whether they happen concurrently or not ... no state is ever stored on the graph instance and the graph instance isn't ever mutated during any execution" (maintainer, [discussion #1211](https://github.com/langchain-ai/langgraph/discussions/1211), also [#1454](https://github.com/langchain-ai/langgraph/discussions/1454)). Single module-level compiled instance + per-invoke `thread_id` is the vendor-served pattern. `config={"max_concurrency": N}` bounds intra-run parallelism.
- **Runtime context API (v0.6+, present in our 1.0.5)**: `StateGraph(State, context_schema=Ctx)`; invoke with `graph.invoke(inputs, context={...})`; nodes/tools take `runtime: Runtime[Ctx]` exposing `.context`, `.store`, `.stream_writer`. This is the sanctioned replacement for smuggling per-request deps through `config["configurable"]` — the natural carrier for per-turn expert config, model handle, workspace credentials.
- Per-invoke dynamic tool binding: since tool sets are baked into the compiled graph today (per-job `build_phase_alternation_graph`), compile-once requires either (a) binding model+tools inside the node from `runtime.context` (model.bind_tools per call — cheap; the LLM call dominates), or (b) one compiled graph per expert config, cached (config space is small: ~5 experts × phase). JS-only contamination bug for the record: [langgraphjs #2040](https://github.com/langchain-ai/langgraphjs/issues/2040) (AsyncLocalStorage leak across concurrent invokes) — Python contextvars path has no equivalent open issue found.

## 5. Gotchas from issues/discussions
1. **No cross-process same-thread coordination in OSS**: "If two processes try to resume the same thread_id simultaneously ... LangGraph has no built-in coordination to prevent both from executing" ([Diagrid analysis](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)); concurrent writers to one thread_id cause destructive "checkpoint collisions"/write-skew ([azguards](https://azguards.com/distributed-systems/mitigating-checkpoint-collisions-write-skew-in-langgraph/)). The doc's lease is **the** correctness mechanism, not an optimization; the Platform's ≤1-run-per-thread queue is the vendor's same answer.
2. **thread_id hygiene**: mixed thread_id formats in `checkpoint_writes` → partial state loss ([#6623](https://github.com/langchain-ai/langgraph/issues/6623)); a user's `CompiledGraph`+AsyncPostgresSaver exceptions resolved by switching to UUID thread_ids ([#4214](https://github.com/langchain-ai/langgraph/issues/4214), closed). Our `thread_id=job_id` (UUID) is fine — keep it canonical, never derive variant forms.
3. **Send objects not serializable** → checkpointer failures ([#6789](https://github.com/langchain-ai/langgraph/issues/6789)) — keep only msgpack-safe types in state.
4. **Large state = flaky saver**: multiple reports tie pipeline/SSL errors and latency to big per-step INSERTs; keep artifacts out of state (we already do — workspace files live on the workspace pod).
5. **TTL sweeper eventual consistency** (#6686) — after adopting TTL-style sweeping, don't trust listings to reflect deletions immediately.
6. **`interrupt()` re-runs node-from-start** (§3.3) — any batch edge must be a superstep boundary, not intra-node.

## 6. Fit to this codebase (worker lane vs. session lane)
- All of §2–§3 lands on the **worker** lane only: sessions (`thread_messages`) have no LangGraph checkpointer, exactly as the doc says (its point 4 holds up).
- The doc's "compile the graph once per process, invoke per request with thread_id — that is how LangGraph Platform itself serves graphs" is confirmed **as a statement about the framework**, but today's `src/agent.py` doesn't do it (graph built per job, tools baked in). The gap is ours, not the framework's — worth stating in the doc so S3 scopes the refactor.
- The Platform worker's knobs map ~1:1 to the doc's missing pieces: lease ↔ run lease; batch requeue ↔ retriable-failure requeue resuming "from the last checkpointed step"; drain ↔ `BG_JOB_SHUTDOWN_TIMEOUT`; journal SSE ↔ Redis pub/sub + `Last-Event-ID`; queued input ↔ enqueue double-texting policy. The doc can cite this as prior art for every contested design point.

## design_implications
- Batch-break mechanism (Workers §, 'Batch driver'): specify astream(stream_mode="updates") + superstep counter + break as the batch driver — yields are per-superstep, and (verified in langgraph 1.0.5 source) closing the generator unwinds AsyncPregelLoop's exit stack and flushes pending durability="async" checkpoint writes before returning; resume with ainvoke(None, config). Explicitly reject recursion_limit as the edge (GraphRecursionError is error-shaped, aborts the in-flight superstep, indistinguishable from runaway) but keep it as a backstop; note per-invoke interrupt_before=["handle_transition"] as a zero-code phase-boundary edge option.
- Add a durability line to the batch driver: run worker batches with the default durability="async" (crash window ≈ 1 superstep, matching the doc's accepted replay semantics) and state the invariant 'the lease is released only after the astream generator has fully closed' — that close is what guarantees the checkpoint flush. Never durability="exit".
- Strengthen the lease section from design choice to correctness requirement, citing that OSS LangGraph has zero cross-process coordination for one thread_id (documented checkpoint-collision/write-skew failures) and that LangGraph Platform's own queue enforces at-most-1-run-per-thread via worker leases — i.e. the vendor's production system is the same design (Postgres run queue + lease + resume-from-last-checkpoint on retriable failure, drain via a shutdown timeout ~180s default).
- Add a 'Checkpointer connection layer' item under What's missing/Workers: replace the current per-job single AsyncConnection (src/agent.py:1279) with one process-wide psycopg AsyncConnectionPool (autocommit=True, prepare_threshold=0) wrapped in a retry-on-connection-error saver subclass (the community ResilientAsyncPostgresSaver pattern — the stock class has no resilience and stale-connection SSL errors are a top failure mode); PgBouncer transaction-mode once replicas grow; never pipeline=True (documented AsyncPipeline [BAD]/SSL failures behind poolers).
- Add a dependency-hygiene note: pin langgraph-checkpoint-postgres to 3.x exactly (requirements.txt currently says >=1.0.0; CVE-2025-64439 RCE in the pre-3.0 json-fallback deserializer) and set LANGGRAPH_STRICT_MSGPACK=true (checkpoint DB becomes the sole state carrier); treat checkpoint-library upgrades like DB migrations because cross-version resume of old checkpoints has documented breakage — relevant to long-paused jobs resumed after an image bump.
- Add a 'Checkpoint growth' subsection: delete-on-terminal already exists, but add an activity-resetting TTL sweep for abandoned threads (mirror Platform semantics: default_ttl + sweep_interval, clock resets on activity), and name ShallowPostgresSaver (latest-checkpoint-only) as the blobs-bloat option for the worker lane since batch-resume only needs the latest checkpoint — production data point: ~93 checkpointer rows per 2-message conversation, 56MB/week blobs growth in one staging system.
- Sessions §: name the four Platform double-texting policies (reject/enqueue/interrupt/rollback; enqueue is their default; Platform-only, OSS has nothing) and state that the DB-queued-input design implements 'enqueue'; decide and record whether steering ever needs 'interrupt' semantics (Platform's caveat: interrupt leaves partially-issued tool calls that must be handled/removed).
- Open question 2 (streaming terminus): answer it — even LangGraph Platform never streams pod→client directly (workers publish to Redis pub/sub, API servers forward SSE; reconnect via Last-Event-ID; runs.join_stream is unbuffered and lossy on late join). Journal-only is the vendor-validated terminus; close the question.
- Compile-once §/Python-now §3: add that compiled graphs are officially thread-safe/stateless (maintainer-confirmed) so one module-level compiled graph per process is safe, and that today's src/agent.py builds the graph per job with tools baked in — S3 must either resolve per-turn model+tools from the Runtime context API (context_schema/Runtime, in our langgraph 1.0.5) inside nodes, or cache one compiled graph per expert config. The framework gap is zero; the refactor is ours.
- Replay-semantics §: add two framework facts — (a) pending_writes means successfully-completed sibling nodes of a crashed superstep are not re-run on resume (bounds duplicate tool executions before v2 idempotency ships); (b) dynamic interrupt() re-runs the interrupted node from its start on resume, so any HITL/batch edge must sit at a superstep boundary, never intra-node.
- Add small hygiene notes: keep thread_id=job_id as the single canonical UUID form everywhere (mixed thread_id formats have caused partial-state loss; non-UUID ids caused saver exceptions); keep state msgpack-safe and artifact-free (Send objects and large payloads are documented saver failure modes); if any dependency bump crosses langgraph 1.0.6, note the recursion_limit default changed 25→1000 (we set it explicitly, so informational).

## surprises
- Double-texting (reject/enqueue/interrupt/rollback) is LangSmith-Platform-only — the OSS framework ships none of it, so the doc's DB-queued-input design isn't duplicating a framework feature, it's implementing the missing 'enqueue' policy.
- astream-and-break is safer than commonly assumed: verified in installed langgraph 1.0.5 source that closing the stream generator awaits pending async-durability checkpoint writes (AsyncPregelLoop.__aexit__ unwinds the exit stack; cancellation deliberately bubbles the exit task so the caller can await it before reusing the DB connection). This makes it a clean batch edge, not a hack.
- dynamic interrupt() resume re-runs the interrupted node from its beginning — code before the interrupt executes again on every resume. Any batch/HITL edge must be a superstep boundary.
- Even LangGraph Platform never streams pod→client directly — workers publish to Redis pub/sub and API servers forward SSE with Last-Event-ID resume. The doc's 'journal-only' open question is answered by the vendor's own architecture.
- requirements.txt pins langgraph-checkpoint-postgres>=1.0.0 while pre-3.0 has an RCE (CVE-2025-64439) in checkpoint deserialization; the fix (3.0) also removed the json/pickle fallback and changed the serde protocol — a silent-image-rebuild version jump could both expose and break long-paused-job resumes.
- AsyncPostgresSaver has no built-in connection resilience — the current per-job single AsyncConnection in src/agent.py is the fragile pattern; production users converge on a shared pool + retry-wrapper subclass, and pipeline mode is actively broken behind poolers.
- recursion_limit default changed 25→1000 in langgraph 1.0.6 (repo is on 1.0.5 with an explicit 1000000 override, so currently unaffected).
- Checkpoint growth is worse than the doc assumes for long worker jobs: ~93 checkpointer rows per 2-message conversation in one production report; checkpoint_blobs stores every state key at every version. ShallowPostgresSaver (latest-checkpoint-only) exists and fits the batch-resume model exactly.
- The local venv doesn't even have langgraph-checkpoint-postgres installed (imports fail) — consistent with the known 'local pytest failures are env noise' pattern, but means no local verification of checkpointer behavior is possible outside the image/k3d.
