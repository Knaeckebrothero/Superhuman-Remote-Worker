# Research: OQ2 (streaming terminus), OQ5 (prompt caching), OQ6 (deployment shape), Sessions gaps

## MISSION A — Streaming through a DB journal: VALIDATED, with two required additions

### A.1 The codebase already does journal-only token streaming end-to-end (this is not a proposal, it's the shipped path)

- Token production: `llm_with_tools.astream(prepared)` → per-chunk `callbacks.on_token(text)` (`src/persistent_graph.py:1675,1091`) → `_loop_on_token` → `_broadcast("token", {...})` (`src/api/persistent_app.py:4322-4323`).
- `_broadcast` (persistent_app.py:3653-3695) synchronously allocates `(epoch, seq)` from module globals `_events_epoch`/`_next_seq`, fans out to WS subscribers (drop-oldest on full queue, "token-stream pacing semantics"), and enqueues an immutable journal snapshot per event — **one thread_events row per token**.
- `_OrderedPersistentEventWriter` (persistent_app.py:3350+) is a single per-runtime writer task: FIFO batches up to `THREAD_EVENT_WRITER_BATCH_SIZE=100` (queue max 10,000), one atomic `INSERT ... FROM jsonb_array_elements($2::jsonb) WITH ORDINALITY` per batch (persistent_app.py:3364-3375). Ordinary streaming frames get one best-effort write; `canvas.*` state invalidations get bounded retries (3 attempts, 0.1s base).
- Consumption: orchestrator SSE `GET /api/persistent/threads/{id}/stream` (orchestrator/main.py:30529-30777) polls `thread_events` with `seq > cursor ORDER BY seq LIMIT 500`. **When rows are found it loops immediately with no sleep**; adaptive backoff only on empty polls: 200ms × 5, then 1s (main.py:30744-30746). Keepalive ping every ~20s idle; zombie-epoch recheck after 2s accumulated idle (`THREAD_EVENTS_EPOCH_RECHECK_S`, main.py:30524).
- Resumability: `Last-Event-ID: <epoch>:<seq>` (header on native browser reconnect, `?last_event_id=` on initial connect since EventSource can't set headers), `gone_beyond_horizon` on epoch mismatch / cursor-older-than-retention / mid-stream epoch bump, no-cursor attach anchored past last `turn.completed` (main.py:30489-30514). A retention prune sweeper exists (main.py:30937+).

So for OQ2 the honest framing is: **journal-only is the current production terminus for cockpit SSE (chunk 3); direct pod→client exists only in the legacy WS path (`_fan_out_live_frame`)**. Statelessness deletes the WS path's reason to exist, not the SSE path.

### A.2 Latency math (current numbers)

Pipeline: LLM chunk → `_broadcast` enqueue (~0, sync) → batch INSERT (in-cluster asyncpg, ~1–5ms; batch drains whatever is queued, so no artificial batching delay) → SSE poll pickup → client.

- **Mid-stream (tokens flowing):** poller sees rows most iterations and re-queries immediately. Inter-chunk gaps (20–50ms typical) mean occasional empty polls → 200ms sleeps → tokens are delivered in bursts of up to ~200ms worth. Added latency: **~5–205ms jitter, ~100ms median**. Perceptually fine (≥5 paints/s); this is what runs today.
- **First token after idle (the case that matters for TTFT):** the poll has backed off to 1s after 5×200ms empty polls. Worst case **+1s on time-to-first-token**, plus write latency. At the doc's S1 acceptance "create-to-first-token < 2s", a stray +1s eats half the budget.
- **200ms flat poll vs 1s backoff:** flat 200ms caps added TTFT latency at ~200ms at the cost of 5 QPS/connection of trivial indexed reads. 100 open SSE connections = 500 QPS of `SELECT ... WHERE thread_id=$1 AND epoch=$2 AND seq>$3 LIMIT 500` — cheap but nonzero; the backoff exists for good reason at idle-heavy duty cycles.
- **Cheapest fix, no NOTIFY needed for sessions:** the orchestrator *receives the user input* (`POST /api/persistent/threads/{id}/input`, main.py:30787). It can wake/reset its own SSE pollers for that thread to the 200ms tier when a turn starts (in-process signal per replica; or a "turn in-flight" flag read on the epoch-recheck cadence). Push-shaped turn start makes a wakeup bus unnecessary for the interactive path.

### A.3 Postgres-as-event-stream at token rates: write amplification is fine; NOTIFY-per-token is the one trap

- Row volume: 50 concurrent *actively streaming* sessions × ~50 tok/s = 2,500 rows/s, arriving as ≤25 batched INSERTs/s per pod. DBOS measured a plain-insert+batched-notify queue at **60k writes/s** on Postgres before CPU saturation ([DBOS](https://www.dbos.dev/blog/postgres-listen-notify-scalability)); our worst case is ~2 orders of magnitude below that. Retention pruning already bounds table growth.
- **recall.ai's "LISTEN/NOTIFY does not scale"** ([recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale), [Simon Willison](https://simonwillison.net/2025/Jul/11/postgres-listen-notify/)): any transaction issuing NOTIFY takes a **global exclusive lock at commit** (to preserve commit-order queue semantics), serializing ALL commits on the instance under heavy concurrent writers — they took three outages. DBOS's rebuttal ([DBOS](https://www.dbos.dev/blog/postgres-listen-notify-scalability)) quantifies it: per-row trigger-NOTIFY capped at **2.9k writes/s**; batched/coalesced NOTIFY (one notify per flush, payload-free ping, data read from the table) reached 60k writes/s with 15–100ms wakeup latency. Consensus pattern: **NOTIFY as wakeup ping only, never as data carrier, never per-row; poll as fallback for missed notifications** (also the 8KB payload limit and no-delivery-to-disconnected-listeners make it a ping, not a log — [Stacksync](https://www.stacksync.com/blog/beyond-listen-notify-postgres-request-reply-real-time-sync)).
- Applied here: if NOTIFY is added at all, notify **once per writer batch flush** (≤25/s across the fleet per 50 active streams — nowhere near the lock-contention regime), payload = thread_id only, orchestrator LISTENs on one connection per replica and nudges the matching pollers. For the worker pull-queue (doc's routing section), NOTIFY-on-enqueue + poll fallback is exactly the DBOS-endorsed pattern and the codebase already runs LISTEN/NOTIFY elsewhere (`orchestrator/services/session_wake.py`, `canvas_session_notifications.py`, migration 0005).

### A.4 SSE resumability: our cursor design matches the industry shape

- **OpenAI background mode** ([docs](https://platform.openai.com/docs/guides/background)): `background=true&stream=true`; every event carries `sequence_number`; resume via `GET /v1/responses/{id}?stream=true&starting_after=<seq>`. Semantically identical to our `epoch:seq` + replay. They enforce a **5-minute resume window** ([community report](https://community.openai.com/t/stream-background-this-response-can-no-longer-be-streamed-because-it-is-more-than-5-minutes-old/1372287)) — the equivalent of our retention floor + `gone_beyond_horizon`. Validates cursor-replay-from-store as the terminus at OpenAI's scale.
- **Vercel `resumable-stream`** ([repo](https://github.com/vercel/resumable-stream), [Ably teardown](https://ably.com/topic/ai-stack/vercel-ai-sdk-resumable-stream-what-it-covers-and-what-it-doesnt)): Redis-backed; common case costs one INCR + SUBSCRIBE per stream; a resuming reader publishes a pubsub request that makes the producer re-send; single-purpose (page-reload during one generation), producer must still be alive for live tail, Redis to operate. It solves a narrower problem than thread_events already solves (no cross-turn history, no multi-device, no epoch semantics). Nothing to adopt.
- **Ably's write-amplification critique** ([Ably](https://ably.com/blog/ai-chat-stream-resumption)): "you pay to persist every token of every response to support the small subset that drop." **Does not apply here**: the journal is already the system of record and the transport; persistence is a sunk cost, not an add-on for resumability.

### A.5 Escape hatches: what Redis Streams / NATS JetStream would buy, and the precedent

- **LangGraph Platform** ([self-hosted docs](https://docs.langchain.com/langsmith/deploy-standalone-server), [neuralware analysis](https://neuralware.github.io/posts/langgraph-redis/)): requires **Postgres AND Redis**. Postgres: assistants/threads/runs/checkpoints + run queue with exactly-once semantics. Redis: (1) pub/sub broker streaming live output from background runs to the API layer, (2) worker wakeup — run row inserted into PG, sentinel pushed to a Redis list, worker BLPOPs, then **fetches the actual run data from Postgres**. I.e., even LangGraph keeps data in PG and uses Redis only as the wakeup/fan-out plane — the exact "ping not payload" split. They added Redis because they're multi-tenant SaaS with high fan-out; it is the proof that journal-in-PG is the right substrate and a broker is an *optional accelerator*.
- **Redis Streams**: fine to ~10k msg/s, XREAD consumer groups, but adds a stateful service + persistence config + another failure domain; **NATS JetStream**: sub-ms tails, single binary, durable consumers ([comparison](https://dev.to/young_gao/real-time-event-streaming-kafka-vs-redis-streams-vs-nats-in-2026-34o1)) — and NATS already exists in this stack (sudo gate, session events via `emit_session_event`, VM provisioner), making JetStream the cheaper escape hatch *if ever needed*. Trigger conditions to write into the doc: sustained journal insert rate approaching ~10k rows/s, or SSE poll read QPS materially loading PG (hundreds of concurrent streams × 5 QPS).

### A.6 GAP the doc misses: seq/epoch allocation must move out of process memory

`_next_seq`/`_events_epoch` are module globals allocated synchronously per attached runtime (persistent_app.py:255-257, 3665-3668), and **epoch is bumped on every agent (re-)attach** (`_resolve_event_journal_epoch`, persistent_app.py:1476). Under stateless turn execution, "attach" happens every turn — naive reuse bumps the epoch per turn, firing `gone_beyond_horizon` re-anchors at the client on every turn. A stateless executor needs: seq continuation within a stable epoch across pods (e.g. `UPDATE threads SET events_seq = events_seq + $n RETURNING` under the turn lease, or fenced allocation stored on the lease row), with epoch bumps reserved for actual recovery/reset. The lease token can double as the write fence (reject journal batches from an expired lease — prevents a zombie pod double-writing seqs).

## MISSION B — Python multi-turn multiplexing: easier than the doc implies for the framework, wider than it implies for persistent_app.py

### B.1 LangGraph / langchain framework layer: no blocker, officially supported

- **Compiled graphs are explicitly thread-safe and concurrency-safe**: "It is entirely safe to share a compiled graph between executions, whether they happen concurrently or not... No state is ever stored on the graph instance, and the graph instance isn't ever mutated during execution" (maintainer, [langgraph#1211](https://github.com/langchain-ai/langgraph/discussions/1211), also [langchain#23630](https://github.com/langchain-ai/langchain/discussions/23630), [langgraph#1454](https://github.com/langchain-ai/langgraph/discussions/1454)). One compiled instance + `config={"configurable": {"thread_id": ...}}` per concurrent `ainvoke` is the documented serverless pattern; state isolation is entirely via checkpointer namespace per thread_id. This confirms the doc's §"Python now" point 1 with citable authority.
- **Per-config compiled-graph caching**: our graphs close over the resolved LLM instance and bound toolset (`src/core/loader.py:3220-4084` builds `ReasoningChatOpenAI`/`ChatAnthropic` per config), so the cache key is (expert-config hash, model id, tool bindings) — not just "the graph." Memory per entry is small (graph topology + prompt strings + client refs, ~KBs–low MBs); the real resource is the HTTP client behind each LLM instance (next point).
- **Shared model clients**: httpx `AsyncClient` is task-safe and thread-safe; the guidance from both httpx and openai-python is **one shared client per process** for pool reuse ([httpx#1633](https://github.com/encode/httpx/discussions/1633), [httpx async docs](https://www.python-httpx.org/async/)). Constraints: (1) pools are **not shareable across event loops** — fine, one loop per pod; (2) httpx has known poor throughput under high concurrency vs aiohttp ([openai-python#1596](https://github.com/openai/openai-python/issues/1596)) — openai SDK supports an aiohttp backend, and pool limits are tunable (`httpx.Limits(max_connections=..., max_keepalive_connections=...)`). Design consequence: when caching N per-config LLM instances, pass one process-wide `http_client` into construction instead of letting each `ChatOpenAI` build its own pool — otherwise N configs × default pool = connection explosion. Today's loader does not do this (each instance builds its own client); harmless at one-turn-per-pod, required for multiplexing.

### B.2 contextvars: the right tool, with three known traps

The codebase already uses the pattern: `_log_context: contextvars.ContextVar` with token-based `bind_log_context`/`reset_log_context` (src/core/logging_config.py:35-73; used per-loop-task at persistent_app.py:535,576). Per-request isolation is automatic — each `asyncio.create_task` copies the current context. Traps documented in the wild: (1) **Starlette middleware runs layers in an anyio task group, so ContextVar sets inside inner middleware don't propagate outward** ([fastapi#8628](https://github.com/fastapi/fastapi/discussions/8628), [fastapi#13120](https://github.com/fastapi/fastapi/discussions/13120)) — set request-scoped vars in the endpoint/dependency, not across middleware layers; (2) forgetting `reset(token)` in a finally leaks context into pooled/reused tasks; (3) sync dependencies run in a threadpool get a context *copy* — writes don't propagate back ([discuss.python.org](https://discuss.python.org/t/back-propagation-of-contextvar-changes-from-worker-threads/15928)). None of these blocks the design; background tasks spawned per-turn (`asyncio.create_task(emit_session_event(...))`, persistent_app.py:3680) inherit the turn's context correctly *but also pin object lifetimes* — a spawned task holding the session object outlives the turn, which is exactly the doc's "background tasks re-homed" item seen from the memory side.

### B.3 The actual de-globalization surface

`persistent_app.py` (~4600+ lines) holds the session in ~15+ module globals: `_agent`, `_session`, `_thread_id`, `_sessions_served`, `_events_epoch`, `_next_seq`, `_event_writer`, WS subscriber sets, permission-batch maps (`tool_call_id → row id`, persistent_app.py:4513+), input queue, exit scheduling (`_schedule_exit`, :720). The mechanical refactor is "wrap in a SessionRuntime object keyed by thread_id + a current-session ContextVar" — not conceptually hard, but every global is a potential cross-session bleed under multiplexing, and the permission-batch and exit-scheduling globals encode process-lifetime assumptions. **Verdict: the doc's v1 "one active turn per pod" is the right call; the deferred multiplexing work is medium, not hard, and is dominated by persistent_app.py bookkeeping, not by LangGraph or the HTTP clients.** A useful sizing statement for the doc: framework layer = zero work (already safe); model-client layer = one shared-http_client change; app layer = one focused refactor of a known global list.

## MISSION C — Provider prompt-cache affinity across pods (2026 semantics)

### C.1 Anthropic — pod identity irrelevant; byte-identity and TTL are everything

Authoritative (claude-api skill, current docs): cache is a **prefix match over the exact rendered bytes** (`tools` → `system` → `messages` order); keyed by content + model (**model-scoped** — switching models invalidates), scoped to the **organization/API key**, served provider-side. Nothing in the semantics references the calling machine, connection, or client identity — any pod presenting the same org key, same model, and byte-identical prefix reads the same cache entry. TTL tiers: **5m default (write 1.25× input price), 1h via `ttl: "1h"` (write 2×)**, reads ~0.1×. Minimum cacheable prefix is model-dependent (512 tokens on Opus 5/Fable 5; 1024 on Opus 4.8/Sonnet 5; 4096 on Opus 4.6/Haiku 4.5). Two agent-loop-relevant constraints: **20-content-block lookback** per breakpoint (a worker superstep turn adding >20 tool_use/tool_result blocks silently misses — place an intermediate breakpoint every ~15 blocks) and **concurrent-request timing** (an entry is readable only after the first response begins streaming — N parallel cold requests all pay full write).

**Verdict: executor-pod identity does NOT affect Anthropic cache hits.** What does: (a) **batch cadence vs 5m TTL** — a `batch_boundary` handoff that re-queues immediately keeps the cache warm; a job that sits paused/pending_review >5m goes cold (already true today, statelessness changes nothing); consider `ttl: "1h"` for jobs whose queue wait can exceed 5m, accepting 2× write; (b) **deterministic prompt reconstruction** — see C.4.

### C.2 OpenAI — automatic, but routing consistency is a real knob a stateless fleet must set

Current guidance ([OpenAI prompt caching docs](https://developers.openai.com/api/docs/guides/prompt-caching), [cookbook "Prompt Caching 201"](https://developers.openai.com/cookbook/examples/prompt_caching_201)): caching is automatic ≥1024-token prefixes; requests are **routed to inference engines by org + hash of the first ~256 tokens**; the KV cache lives on the engine, so hit rate depends on landing on the same engine. `prompt_cache_key` is combined with the prefix hash to increase routing stickiness — one coding customer went **60% → 87% hit rate** by adopting it; the `user` field also aids bucketing ([community thread](https://community.openai.com/t/prompt-cache-routing-the-user-parameter/1267103)). Limit: ~**15 RPM per (prefix, prompt_cache_key) shard** before spillover to other engines causes misses. Cache retention: minutes-scale (5–10 min typical, up to ~1h off-peak).

**Verdict: executor-pod identity does NOT affect OpenAI hits** (routing is server-side by prompt hash, not client connection), **but a stateless design should set `prompt_cache_key` = thread_id/job_id** so all pods serving one thread's turns route consistently. This is a one-line change in the OpenAI-path LLM construction and is the single provider-side knob the doc should mandate. 15 RPM/shard is far above one thread's turn rate.

### C.3 vLLM / SGLang self-hosted — per-engine-instance; multi-replica endpoint is the only case with real work

vLLM Automatic Prefix Caching and SGLang RadixAttention are **GPU-resident, per-engine-instance** caches. With a single-replica endpoint (the homelab reality), every agent pod hits the same engine — pod identity irrelevant, nothing to do. With a **multi-replica LLM endpoint**, each replica has its own KV cache and a plain round-robin LB destroys prefix reuse ([TrueFoundry](https://www.truefoundry.com/blog/kv-cache-routing-why-standard-load-balancers-break-prefix-caching-and-how-to-fix-it)); the ecosystem answers are cache-aware routers: **llm-d precise prefix-cache-aware Endpoint Picker** (pulls live prefix-cache state from instances, [llm-d guide](https://github.com/llm-d/llm-d/blob/main/guides/precise-prefix-cache-aware/README.md)), **vLLM production-stack KV-aware routing** ([docs](https://docs.vllm.ai/projects/production-stack/en/vllm-stack-0.1.7/use_cases/kv-cache-aware-routing.html)), **SGLang cache-aware router**, **Ray Serve PrefixCacheAffinityRouter** ([Ray docs](https://docs.ray.io/en/latest/serve/llm/user-guides/prefix-aware-routing.html)), or **LMCache** for cross-node KV sharing. Note this is a property of the *LLM serving tier*, fully orthogonal to whether agent pods are stateful: today's pinned agent pods already give zero session affinity toward a multi-replica endpoint unless the gateway does it.

**Verdict for OQ5 overall: pod identity never matters, for any provider. The doc's OQ5 hypothesis is confirmed. The real risks are elsewhere — C.4.**

### C.4 The risk the doc should add: deterministic prompt reconstruction IS the cache key

A resident process reuses the same in-memory message list turn after turn — byte-stability for free. A stateless executor **re-renders the prompt from DB state every turn**; any nondeterminism (unsorted `json.dumps`, dict/set iteration order in tool schemas, timestamps injected into system prompts, re-resolution producing differently-ordered tool lists) silently zeroes the cache across *all* providers, at 10× input cost on Anthropic. The known silent invalidators: `datetime.now()` in system prompt, unsorted JSON serialization, varying tool sets/order, per-request IDs early in content. This should be a named requirement in the doc ("prompt assembly must be a deterministic function of (config hash, message rows)") with a verification metric: `usage.cache_read_input_tokens > 0` on turn N+1 as an S1/S3 acceptance criterion.

## OQ6 — Deployment shape (evidence-based inputs)

- Prompt caching is provider-side and content-keyed (C.1–C.3), so **deployment shape has zero effect on cache hits** — removes one argued advantage of per-expert deployments.
- Per-request config resolution already exists at attach granularity (`/session/attach` re-resolves expert config, persistent_app.py:2047), and LangGraph Platform's shape is one generic server resolving assistant config per run — precedent for the generic deployment.
- The one load-bearing separation is **interactive vs worker lanes** (the doc's own priority point): two Deployments sharing one image, or one Deployment + K8s PriorityClass/preemption with HPA on queue depth. Per-expert deployments only earn their keep when resource profiles genuinely differ (e.g., browser-stack memory).
- LangGraph Platform's worker-wakeup design (PG row + wakeup ping, worker fetches row from PG) is the same lease/queue shape the doc proposes — reasonable to cite as convergent design.

## Sessions gaps (misc grounded facts)

- Queued-input-to-DB: `POST /threads/{id}/input` already lands at the orchestrator with a per-turn dedup lock (main.py:30787-30791) before forwarding to the agent pod — the "input as row + wake" flip changes the forwarding half only.
- The event writer's failure surface is already designed for the stateless world: terminal write failure triggers client reconciliation rather than trusting memory (persistent_app.py:3358-3362) — the journal, not the process, is authoritative.
- NATS mirror of notification-worthy events (`emit_session_event`, persistent_app.py:3679-3680) is a per-turn background task that needs a home in the turn-executor model (it's fire-and-forget; safe to run before lease release).

## design_implications
- OQ2 verdict to write in: journal-only streaming is ALREADY the production terminus (cockpit SSE reads thread_events since chunk 3); statelessness deletes the legacy direct WS path, it does not create a new streaming problem. Direct pod→client streaming is never needed; P5/P6 finishes the job.
- Add the missing seq/epoch allocation section: _next_seq/_events_epoch are module globals and epoch bumps on every agent attach — under per-turn attach this would fire gone_beyond_horizon at the client every turn. Require: DB-allocated seq continuation within a stable epoch (e.g. UPDATE threads SET events_seq = events_seq + N RETURNING, under the turn lease), epoch bump reserved for recovery; use the lease token as a journal write fence so an expired-lease pod cannot double-write seqs.
- Recommended streaming numbers: keep per-token journal events with the existing batched writer (batch<=100, single jsonb_array_elements INSERT — ~2.5k rows/s at 50 concurrent active streams, ~25x below DBOS's measured 60k/s plain-insert ceiling); keep the 200ms-active/1s-idle poll, but pin the poll at 200ms while a turn is in-flight — triggered by the input POST the orchestrator itself receives (no NOTIFY infra needed for sessions). Net added latency: ~5–205ms mid-stream, and TTFT no longer eats the 1s idle-backoff penalty.
- If/where NOTIFY is used (worker queue dispatch, cross-replica SSE wake): payload-free ping per writer-batch flush or per enqueue, NEVER per token/row (recall.ai global-commit-lock outages at per-row NOTIFY, 2.9k/s cap vs 60k/s batched — DBOS), always with poll fallback. Cite that LangGraph Platform uses the identical ping-not-payload split (Redis sentinel + fetch-from-Postgres).
- Escape-hatch policy for OQ2: stay Postgres-only; write the trigger metrics into the doc — sustained journal insert rate approaching ~10k rows/s or SSE poll fan-out (connections × 5 QPS) materially loading PG; if triggered, prefer NATS JetStream (already deployed in-stack for sudo/VM/session events) over adding Redis.
- OQ5 verdict to write in: executor-pod identity affects cache hits on NO provider. Anthropic: content+model+org-keyed prefix match, 5m/1h TTL, calling machine irrelevant. OpenAI: server-side routing by org + hash of first ~256 tokens — but SET prompt_cache_key = thread_id/job_id in the OpenAI-path LLM construction (documented 60%→87% hit-rate case; ~15 RPM per key-shard is far above one thread's rate). vLLM/SGLang: per-engine-instance cache — single-replica endpoint needs nothing; a multi-replica endpoint needs cache-aware routing at the LLM gateway (llm-d EPP / vLLM production-stack / SGLang router), which is orthogonal to agent statelessness (pinned pods don't provide it either).
- Add a new hard requirement under OQ5: deterministic prompt reconstruction. A stateless pod re-renders the prompt from DB every turn; any nondeterminism (unsorted json.dumps, tool-list order from config re-resolution, timestamps in system prompt) silently zeroes provider caches at ~10x input cost. Make 'prompt assembly is a deterministic function of (config hash, message rows)' explicit, and add usage.cache_read_input_tokens > 0 on the second consecutive turn/batch as an S1/S3 acceptance criterion.
- Batch cadence vs TTL (workers): batch_boundary immediate re-queue keeps the 5m Anthropic cache warm; jobs that can sit queued/paused >5m go cold (already true today). Optionally use ttl:'1h' (2x write cost) for experts whose queue wait exceeds 5m. Also note the 20-content-block cache lookback: supersteps adding >20 tool blocks per request need an intermediate cache breakpoint every ~15 blocks.
- OQ6 verdict: one generic deployment resolving config per turn, with exactly two lanes (interactive vs worker) as separate Deployments or PriorityClasses, HPA on queue depth. Prompt caching is provider-side so deployment shape cannot affect it; per-expert deployments only when resource profiles differ (browser stack). Cite the existing /session/attach re-resolution and LangGraph Platform's generic-server-per-run shape as precedent.
- Strengthen the 'Python now' section with citable authority: LangGraph maintainers state compiled graphs are safe for concurrent use from one instance (langgraph discussions #1211/#1454); size the deferred multiplexing work honestly as three layers — framework: zero (already safe); model clients: pass one shared httpx.AsyncClient (tuned Limits, optionally aiohttp backend) into all cached per-config LLM instances instead of one pool per instance; app layer: a focused refactor of persistent_app.py's ~15 module globals into a SessionRuntime keyed by thread_id + a current-session ContextVar (the existing bind_log_context token pattern extends; watch the Starlette middleware task-group propagation trap and always reset tokens in finally).
- SSE resume section can cite OpenAI background mode (sequence_number + starting_after cursor replay, 5-minute resume window) as the industry-converged shape identical to the existing epoch:seq + retention-floor + gone_beyond_horizon design — and note Vercel resumable-stream solves a strictly narrower problem (single-generation page reload, Redis-dependent) and offers nothing to adopt.

## surprises
- The doc's OQ2 is already answered by the codebase: journal-only token streaming through Postgres is the shipped production path (per-token thread_events rows, batched writer, 200ms/1s SSE poll with Last-Event-ID cursor replay) — the question is tuning, not feasibility.
- Epoch bumps on every agent attach (_resolve_event_journal_epoch): naive stateless per-turn attach would fire a client-visible gone_beyond_horizon re-anchor on every turn — a concrete gap the doc doesn't mention; seq/epoch allocation must move to the DB under the lease.
- LangGraph Platform does NOT do journal-only streaming — it requires Redis as a pub/sub streaming and wakeup plane alongside Postgres — but its data-in-PG/ping-in-broker split is exactly the DBOS-endorsed pattern, and their worker queue (PG row + sentinel wake + fetch-from-PG) matches this doc's lease design.
- LISTEN/NOTIFY controversy resolved with numbers: per-row NOTIFY caps at ~2.9k writes/s due to a global commit-order lock (recall.ai's outages), while batched payload-free NOTIFY reaches 60k writes/s — so the go_rewrite.md sketch of 'NOTIFY the next worker' is safe only if it is never per-token/per-row.
- The biggest prompt-cache risk of statelessness is not TTL or pod identity but byte-determinism: a stateless pod re-renders the prompt from DB each turn, and any nondeterministic serialization silently zeroes caches on every provider — a requirement absent from the doc.
- OpenAI cache hits DO have a routing-consistency knob (prompt_cache_key, ~15 RPM per shard, documented 60%→87% improvement) — the doc's 'content-keyed so nothing matters' claim is slightly wrong for OpenAI; one line of code (key = thread_id) fixes it.
- OpenAI background mode's resume API (sequence_number + starting_after, 5-min window) is shape-identical to the existing epoch:seq design — independent convergence validating the journal-cursor terminus.
