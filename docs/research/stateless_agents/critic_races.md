# critic-4

## verdict
The doc gets the big model right — recorded lease + fencing token + persist-time checks is the correct shape, and its code citations spot-checked clean (shipped 0054 lease, rewind epoch bump, dispatch ordering/cooldown, freeze-type wiring, the process-local steering dedup). But §5.1-5.4 as written is roughly half of a correct concurrent design: it specifies claim, steal, and fence with rigor while leaving the entire completion half of the lifecycle undefined — no done/consumed/error-release semantics — and that undefined half is where the real double-execution holes live (a legitimately re-claimed turn re-answering after a steal-between-persist-and-complete, token reuse via delete-and-reinsert defeating the 'monotonic per unit' foundation). Three further structural problems would change the design: the epoch-as-lease-token unification is internally contradictory (diagnostics-only leased_by vs the correctness-bearing CASE rule; 2 bumps per steal vs its own ≤1 acceptance assert) and never reconciled with the shipped rewind flow (which assumes a detached thread and writes seq=1 into the new epoch); the fence contract is unimplementable for the checkpoint lane as specified (§5.7's autocommit pool + stock saver leaves no transaction to fence, contradicting §8's 'zero framework work'); and S3 stands up a second lease authority alongside the live jobs.lease_expires_at machinery without ever ruling which one wins — a concrete cross-system double-execution hazard during the migration the doc itself mandates. None of this argues against the direction; all of it argues the doc is not yet build-ready at S1/S3 without a completion-protocol section and an epoch/rewind/lease reconciliation.

## findings (9)

### 1. [CRITICAL] §5.1/5.3.1
**Claim/gap:** The queue lifecycle has no completion half: no done/idle disposition for run_queue rows (state enum is only queued|leased|parked), no consumed-marker for queued input rows, and no error-release path with attempt/backoff semantics. Consequences: (a) at-least-once redelivery after a steal that lands between the final message persist and turn completion RE-EXECUTES a finished turn — duplicate assistant reply and double LLM/tool spend, and the fence cannot help because the re-executor holds a VALID new lease; (b) if completion deletes the row (the natural choice for one-shot session turns), the next enqueue re-INSERTs with lease_token DEFAULT 0 — token reuse that breaks the 'monotonic per unit' fencing foundation; if it instead leaves the row 'queued', idle threads get phantom claims; (c) mid-turn input arriving against a leased row ('enqueues (or refreshes)') has no defined refresh semantics — setting state='queued' on a leased row breaks the lease, leaving it leased strands the input until the undefined completion step.

**Evidence:** Verified doc-internal: schema lines (state enum, lease_token BIGINT DEFAULT 0, unit_id PRIMARY KEY), §5.3.1 'claim delivers … queued input rows' with no consumption contract, §9 S1 'queued input survives and drains FIFO' with no consume/complete mechanism anywhere in the doc. The house 'session wake outbox' (postgres.py:6016+, 'the claim exists because the send is NOT idempotent … Claim first, commit, then send') shows the repo already knows a status-CAS is insufficient for non-idempotent sends — an LLM turn is maximally non-idempotent and gets no equivalent here.

**Fix:** Specify the fourth lifecycle statement: turn completion = one fenced transaction containing final message persist + input-consumed watermark (e.g. consumed thread_messages.seq recorded on the queue row) + row disposition (state='done' or DELETE with the token preserved on threads.events_epoch/jobs); re-claims must check the watermark before invoking the LLM (skip-if-already-answered); define voluntary error-release SQL with attempt/backoff (today backoff exists only in the reaper); define enqueue-against-leased-row as 'set a pending flag; completion requeues if unconsumed inputs exist'.

### 2. [CRITICAL] §5.4/4.3/9-S3
**Claim/gap:** Two lease authorities for one job. S3 gives worker batches a run_queue lease while the SHIPPED jobs-row lease (migration 0054) stays live, and the doc never says whether run_queue replaces it, dual-writes it, or partitions from it. If a stateless claim does not maintain jobs.lease_expires_at (it can't easily: renewal is fenced by assigned_agent_id, a registered-agents FK identity stateless pods no longer have), recover_expired_lease_jobs pauses the job mid-batch and _trigger_dispatch hands it to the kept registered-agent path (§7 keeps it for compose/officers/rollback) → concurrent double execution across the two systems; the run_queue fence is invisible to legacy agents, which never check it. Conversely nothing stated stops the legacy auto-assign dispatcher from claiming a batch_boundary-released job: claim_job_for_agent's CAS predicate (assigned_agent_id IS NULL AND status IN ('created','paused')) matches a released batch exactly.

**Evidence:** Verified in code: recover_expired_lease_jobs (orchestrator/database/postgres.py:5504-5538) pauses ANY processing job with expired lease_expires_at, no flag exempting stateless jobs; claim_job_for_agent (postgres.py:5933-5977) and renewal fenced by assigned_agent_id (postgres.py:5235-5260). Doc §4.3 lists the shipped lease as substrate and §9 S3 says 'pull-claim + claim-token renewal + stage-4 completion CAS', but no sentence resolves which reaper/lease wins or how the migration-phase flag partitions dispatch.

**Fix:** Add an explicit ruling to §5.4: for stateless-flagged jobs, run_queue is the sole lease authority — the claim transaction also sets jobs.status/assigned marker atomically, recover_expired_lease_jobs and the legacy dispatcher exclude the flag in their WHERE clauses (a dispatch-exclusion predicate, not just a rollout toggle), and the stage-4 completion CAS keys on run_queue.lease_token, not assigned_agent_id. Alternatively specify dual-write (claim/renew/release touch both tables in one transaction) and which expiry sweep is authoritative.

### 3. [CRITICAL] §5.3.2/5.2
**Claim/gap:** Epoch-as-lease-token unification is underspecified against rewind and contradicts itself. (1) Rewind: the doc lists rewind as an epoch-bump cause but never defines its effect on an ACTIVE lease. Under unification, the orchestrator-side rewind bump fences the live holder (good), but with unit_id=thread_id as PRIMARY KEY there is exactly one queue row, still 'leased' with a stale token — the post-rewind turn cannot claim until the reaper reaps (~60-90 s stall after every mid-turn rewind), unless rewind also steals the lease, which is unspecified. (2) The shipped rewind writes a thread_events row at (new_epoch, seq=1) and its safety docstring requires 'no agent event-writer to collide with' (detached thread); with stable epochs a same-pod re-claim does NOT bump, so the next writer shares the rewind's epoch — whether the DB-side seq allocator starts above the rewind's seq=1 is unspecified, and the natural per-epoch-restart implementation hits the UNIQUE (thread_id, epoch, seq) index, presenting as §5.3.2's 'lost lease, terminal-fail loudly' false positive. (3) The CASE bump rule makes leased_by/lease_owner correctness-bearing for epoch stability while the schema comment says 'diagnostics only, never correctness' (and the doc uses three names: leased_by, lease_owner, last_pod). (4) The reaper always bumps and the post-steal claim bumps again (reaper sets leased_by=NULL → NULL IS DISTINCT FROM $pod) — 2 bumps per steal, violating the doc's own S1 acceptance criterion 'assert ≤1 per steal'.

**Evidence:** Verified in code: apply_thread_rewind (postgres.py:7916-7995) — advisory lock, epoch bump, INSERT thread_events (epoch, seq=1, 'rewind.done'), docstring 'safe precisely because the thread is detached'; UNIQUE idx_thread_events_thread_epoch_seq (schema_current.sql:9747, migration 0004). Verified doc-internal: §5.1 'leased_by … diagnostics only, never correctness' vs §5.3.2 CASE rule; reaper SQL sets leased_by=NULL then claim CASE fires.

**Fix:** Specify rewind as a fenced lease steal: one advisory-locked transaction bumps events_epoch, resets/clears the run_queue lease (state='queued', token follows epoch), and initializes the per-epoch seq allocator above the rewind.done row; change the schema comment or the CASE rule so exactly one artifact owns writer-generation truth; make the reaper's bump the ONLY steal bump (claim after steal must not re-bump — e.g. CASE on a generation column, not on pod name vs NULL); pick one column name.

### 4. [MAJOR] §5.2/5.7/8
**Claim/gap:** The fencing contract ('every persist transaction … opens with SELECT … FOR SHARE') is unimplementable as stated for the checkpoint lane, and the doc ignores the torn-turn window between fenced transactions. §5.7 mandates a process-wide psycopg pool with autocommit=True feeding the STOCK AsyncPostgresSaver (plus a retry wrapper) — under autocommit each of aput's statements commits independently; there IS no 'persist transaction' to open with a fence. Fencing checkpoint puts requires a custom saver subclass wrapping fence+put in an explicit transaction block, contradicting §8's 'Framework: zero work.' Separately, a turn's durable footprint spans multiple transactions on different connections (checkpoint put, thread_messages insert, completion/outbox); each is individually fenced but a steal BETWEEN them leaves half-persisted turns (checkpoint advanced, messages/completion absent → finding-1's re-run). The doc's honesty paragraph covers workspace side effects only, never the DB-side torn boundary.

**Evidence:** Verified doc-internal contradiction: §5.2 fence text lists 'checkpoint put' as a fenced transaction; §5.7 specifies autocommit=True pool + stock-saver-with-retry and 'never pipeline=True'; §8.1 claims zero framework work. Cross-transaction gap follows from §5.2's own per-transaction fence design. Saver internals (aput as multiple autocommitted statements) are plausible, from the vendor-pattern description in web_langgraph-serverless.md, not read from library source.

**Fix:** Name the atomic unit explicitly: final-message persist + completion/outbox must share one fenced transaction (finding 1); checkpoint fencing via a thin saver subclass that opens conn.transaction() around fence+put (add it to the S3 build list and correct §8.1 from 'zero work' to 'one saver subclass'); state the accepted invariant for the remaining gap (checkpoint-ahead-of-messages is safe because the new claimant rebuilds from checkpoint alone for workers / messages alone for sessions — and verify that claim per lane).

### 5. [MAJOR] §5.2
**Claim/gap:** The reaper is a single UPDATE over ALL expired rows, and the doc's own FOR SHARE fence makes it head-of-line blocking: the steal UPDATE waits on any in-flight persist's FOR SHARE, so one wedged persist transaction (network partition mid-commit, idle-in-transaction — the exact hazard class §5.2 itself cites) blocks steals for EVERY other expired unit until it times out. Rescue latency for the whole fleet degrades to the slowest zombie's transaction timeout.

**Evidence:** Verified doc-internal: reaper SQL (§5.2) has WHERE state='leased' AND leased_until < now()-30s with no row-skip; fence is SELECT … FOR SHARE held to persist commit; PG UPDATE blocks on FOR SHARE row locks row-by-row, stalling the statement mid-scan.

**Fix:** Rewrite the reaper as the same CTE claim shape it preaches: SELECT unit_id … WHERE expired FOR UPDATE SKIP LOCKED, then UPDATE FROM — per-row steals that skip rows currently pinned by a live persist (they'll be stolen next 15 s tick), so one wedged writer never delays unrelated rescues.

### 6. [MAJOR] §5.2
**Claim/gap:** attempt-reset-on-any-successful-persist breaks max_attempts and the backoff for partially-progressing poison units: a turn that reliably streams a few journal frames (or lands one checkpoint) before crashing at the same tool call resets attempt every cycle → never parks, and run_after backoff (2^attempt) resets to ~1-2 s → an infinite hot crash-loop burning LLM spend each iteration. 'parked' only isolates zero-progress poison. The doc presents the reset as purely protective ('partial progress never parks a unit') without the failure mode.

**Evidence:** Verified doc-internal: reaper backoff formula is keyed on attempt (§5.2 steal SQL) and 'any successful persist resets attempt' is stated unconditionally two lines later; nothing else bounds retries (no wall-clock or attempts-since-completion cap for sessions; the batch wall-clock cap in §5.4.3 is only 'consider'ed for workers).

**Fix:** Reset attempt only on full turn/batch completion, or park on attempts-since-last-completion plus a per-unit wall-clock/cost budget; make the reset UPDATE itself carry the lease_token fence; add 'poison unit with partial progress parks within N cycles' to the S1 acceptance list.

### 7. [MAJOR] §5.3.5/5.1
**Claim/gap:** The dedup unique index spans state IN ('queued','leased'), so a collapsible bg task enqueued while its predecessor is RUNNING is silently dropped: turn N+1 commits and its cloud_push:<thread> outbox insert dedups into the in-flight push row whose tree-walk may already be past the changed files → the final push of a session can be lost — exactly the lost-push/concurrent-walk class the 08-06 fix (99b87008) closed and that §5.3.5's own ordering-fence paragraph worries about. The outbox guarantee 'turn committed ⟺ follow-up enqueued' quietly becomes '…⟺ follow-up enqueued OR swallowed by a running predecessor'.

**Evidence:** Verified doc-internal: idx_run_queue_dedup includes 'leased' (§5.1) while §5.3.5 sells the outbox as fixing lost pushes and separately demands a push(N)→pull(N+1) ordering enforcer; web_pg-queue-lease.md's River unique-by-state note is the pattern's known caveat. Impact on the shipped push path is plausible (depends on when the push snapshots the tree), but the design-level lost-signal is certain.

**Fix:** Dedup on state='queued' only (an enqueue during a leased predecessor creates a successor row — at most one PENDING push, which is the actual invariant wanted), or require collapsible executors to re-read a per-mount sync-generation at execution start and self-requeue if it moved.

### 8. [MAJOR] §5.4.3/5.4.1
**Claim/gap:** Steering-without-heartbeat reuses a drain path whose exactly-once-ness is process-local, which batch rotation breaks in both directions: the DB-direct phase-boundary drain dedups against tool_context._delivered_reply_keys (an in-process set) precisely because the natural-break ack is fire-and-forget; a batch release + re-claim on another pod re-delivers already-delivered guidance (empty set on the successor, ack not yet landed), and conversely an ack that landed while the injected message only reached un-checkpointed state (durability='async', crash window = 1 superstep) LOSES the guidance across a steal. Today these windows open once per crash; under §5.4.1 they open at every batch boundary and every steal.

**Evidence:** Verified in code: src/graph.py:3423-3443 — comment states the two paths race, the ack is fire-and-forget, and the filter is the in-process _delivered_reply_keys set; §5.7 chooses durability='async'. The doc's §5.4.3 presents the DB-direct pattern as ready to swap in with no handoff-safety caveat.

**Fix:** Make reply consumption checkpoint-coupled: ack rows with the checkpoint_id (or superstep watermark) that absorbed them, mark consumed only when that checkpoint is durable, and rebuild the dedup set from checkpointed state on every claim (same companion shape as the TodoManager-hydration fix §5.4.1 already prescribes).

### 9. [MINOR] §5.4.1/5.4.3
**Claim/gap:** batch_boundary overloads 'paused' — today a human-actionable, low-frequency state — as the every-few-minutes rotation state: job status flaps processing↔paused each batch in the cockpit, human actions gated on paused (resume-with-feedback, config edit, cancel) now race the auto-redispatcher at batch cadence, and recover_orphaned_jobs' freeze-shed literal targets paused+unassigned rows. The wiring section adds the freeze type to four lists but never addresses the state-space collision or UI semantics.

**Evidence:** Verified in code that the adopted machinery routes through status='paused' + unassigned (claim_job_for_agent predicate postgres.py:5969-5970; recover_orphaned_jobs freeze-shed on paused rows postgres.py:~5486); the race outcomes are plausible (single-winner CAS likely prevents true double-dispatch in the legacy path, but feedback-vs-continuation ordering and UI flap are unexamined).

**Fix:** Introduce a queue-visible sub-state (e.g. paused_reason='batch_rotation' or a distinct 'queued' job status mapped to 'processing' in user-facing surfaces), and specify that human paused-state actions CAS on the reason so a user pause and a rotation release are distinguishable.
