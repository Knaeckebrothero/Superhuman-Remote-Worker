# critic-2

## verdict
The doc is excellent backend engineering that prices the machine's win and never prices the user's experience under contention and failure. From the cockpit seat it has one rollout-blocking omission and three internal contradictions. Omission: S1 promises create-to-first-token < 2 s, but the shipped cockpit gates the composer on a bound-agent handshake (GET /connection 425 → POST /prepare → poll up to 180 s) and receives mode/interrupt acks only over the per-session control WS — the S1 build list and acceptance criteria contain zero client or API-contract work, so S1 as scoped either breaks session-open or must fake the old contract and deliver no visible win. Contradictions: (1) §5.3.2 prices the epoch cascade as fatal per-turn but assumes writer-change bumps are "rare" — the claim formula bumps on every cross-pod re-claim, which is routine exactly at the high utilization the design is sold on, and the acceptance metric ("≤1 per steal") measures steals, not pod switches; (2) the fenced journal admits only the lease holder as writer, yet the reaper (parked/steal notices), re-homed background workers (title.updated flows through _broadcast today), and P6's orchestrator-journaled acks all need to write client-visible frames — a parked turn currently ends as silence with no user-facing terminal event; (3) §7 deletes the live-settings ladder in favor of "write override, next turn resolves fresh," while today mode.set applies to the very next tool call inside the running turn — a safety-adjacent regression the doc doesn't name. Add the unstated capacity trade (a pinned session never waits behind strangers at turn time; a pooled one can, with no queued-turn UX, per-user fairness, or p95 TTFT criterion) and the undefined mid-turn-steal semantics (≤ ~90 s of dead air indistinguishable from a long tool call, partial answer vanishing then re-running with possibly different text, new-to-sessions auto-re-run of side-effectful MCP/datasource calls). None of this argues against the architecture; all of it belongs in acceptance criteria before S1 starts.

## findings (10)

### 1. [CRITICAL] §9/S1 (+2 UX)
**Claim/gap:** S1's acceptance 'create-to-first-token < 2 s' is unrealizable as scoped: the build list contains zero cockpit/API-contract work, but the shipped client cannot even open a session without a bound agent.

**Evidence:** Verified: cockpit/src/app/core/services/persistent-chat.service.ts:1761-1867 — session open runs GET /connection (425 when no agent bound) → POST /prepare → poll /connection up to READY_TIMEOUT_MS=180 s; :1784-1791 the composer unblocks (markSessionReady) only when /connection returns 200, which 'only returns 200 after the orchestrator has a bound agent and the agent's /ready probe passes'. :1930-1937 mode.changed/narration.changed/interrupt.ack arrive only as per-client control-WS sends, never via SSE. sessions-page.component.ts:644-682 create → navigate → this same handshake. Under stateless there is no bound agent: the current client polls /prepare//connection until timeout, and control verbs have no transport until P6 — yet §9/S1 lists only backend items and §7 defers WS retirement to P6 without making it (or a compat shim) an S1 dependency.

**Fix:** Add an explicit S1 workstream: orchestrator-owned /input + a /connection//prepare compatibility answer (immediate 'ready' for stateless threads), composer ungating, removal/bypass of the provisioning card for the stateless class, and a stated S1 dependency on P6 (or a transitional REST path) for mode.set/interrupt/canvas verbs. Put 'existing cockpit build opens and chats against a stateless thread' in S1 acceptance.

### 2. [CRITICAL] §5.3.2 (+9/S1 acceptance)
**Claim/gap:** Epoch-bump frequency is understated: 'with soft affinity the common case re-claims on the same pod and bumps nothing' — but the proposed formula bumps on EVERY writer change, i.e. every cross-pod re-claim, which is routine precisely at the utilization (10 pods : 30-50 sessions) the design is sold on, and each bump costs the client the full cascade. The acceptance metric 'assert ≤1 per steal, not per turn' measures steals, not pod switches.

**Evidence:** Verified: the doc's own claim SQL (`CASE WHEN lease_owner IS DISTINCT FROM $pod THEN 1 ELSE 0 END`) fires on any pod change — load-balanced turn placement, release-at-gate resumption (§10.3 leaning release), capacity-driven affinity misses — not only steals. Cascade cost verified in persistent-chat.service.ts:1628-1680: close SSE → clearThreadMessages (full IndexedDB wipe) → deleteThreadCursor → full loadHistory → redispatch outbox → loadThreadMeta → reopen; plus ~2.0-2.2 s dead-epoch detection when it happens mid-stream (research: main.py THREAD_EVENTS_EPOCH_RECHECK_S). Affinity hit rate is lowest exactly when pods are busiest — the regime that justifies pooling — so the per-turn tax §5.3.2 declares fatal partially returns under load, uncapped and unmeasured.

**Fix:** Either (a) add an acceptance target on cascade frequency/affinity hit rate under a loaded bench (e.g. 'cross-pod re-claim rate < X% of turns at 80% pod utilization; p95 turn TTFT includes cascade cost'), or (b) redesign the client cascade to be cheap on a benign writer change (delta refetch keyed to the re-anchor frame instead of cache wipe — revisiting the research's 'don't take the client shortcut' advice specifically for the non-steal bump), or (c) decouple: bump epoch only on steal/rewind (unclean takeover) and keep seq monotonic across clean cross-pod handoffs now that seq is DB-side, making a clean pod switch invisible to the client.

### 3. [MAJOR] §5.2 / 9-S1 acceptance
**Claim/gap:** 'Pod deleted mid-turn → clean client retry' is undefined; the actual user-visible semantics of a lease steal are never stated: up to ~90-105 s of frozen stream indistinguishable from a long tool call (no signal exists — the SSE is healthy, the writer is dead), then the cache-wipe cascade at the worst possible moment, then the partially-streamed answer VANISHES (dead-epoch deltas are never replayed; the partial message is not in thread_messages) and the turn re-runs, possibly producing different text. Also §5.2's 'replay semantics equal today's crash-resume behavior' is false for sessions: today a crashed session turn is simply lost and the user manually resends; statelessness introduces AUTOMATIC re-run of side-effectful turns.

**Evidence:** Verified: persistent-chat.service.ts:1613-1680 — history reload shows only persisted rows and re-anchors to the new-epoch tail, so dead-epoch deltas (the watched partial answer) are dropped, not duplicated; re-run tokens then replay from the new epoch. Research code_session-residue.md §5: mid-turn/unconsumed state today yields 'answered-by-nothing until they send another' — no auto-re-run lane exists for sessions. §5.2's own fencing-boundary paragraph scopes idempotency to workspace-side tool dedup (v2), leaving S1 lite sessions' MCP/datasource writes (create_job, send_message_to_job, datasource updates) re-executable on retry with no dedup story.

**Fix:** State the steal UX contract in §5.3 and S1 acceptance: (1) a reaper-written 'turn.interrupted/retrying' journal frame at steal so the client can render a state instead of dead air (requires the system-writer carve-out, see next finding); (2) explicitly name 'partial answer disappears and regenerates' as accepted behavior; (3) scope S1 retry policy for side-effectful lite-session tools (e.g. re-run only up to the first tool call, or gate MCP writes behind the v2 idempotency layer) instead of inheriting worker replay semantics that don't hold for sessions.

### 4. [MAJOR] §5.3.2(3) / 5.3.5 / 5.2 reaper
**Claim/gap:** Internal contradiction: the fenced journal admits only the current lease holder as writer, but the design needs non-lease-holders to emit client-visible events — the reaper (steal notice, parked terminal), re-homed background workers (title generation), and P6's orchestrator-journaled 202 acks. Sharpest consequence: a unit that exhausts max_attempts is 'parked … for human attention' with NO user-facing terminal event — the turn silently never answers even though the input POST returned 200 long ago.

**Evidence:** Verified: title updates flow through _broadcast('title.updated', ...) (src/api/persistent_app.py:8233), i.e. they are journal frames today; §5.3.5 re-homes title gen to the outbox queue, whose worker holds no session lease/epoch and under fence rule 3 ('batch INSERT checks threads.events_epoch = $claimed') cannot write the journal. The reaper section defines parked as an admin state only; no turn.error/turn.parked emission path exists anywhere in the doc. Meanwhile §6.4 cites P5/P6 whose orchestrator-side control acks are journaled frames — also unauthored by any lease.

**Fix:** Define a system-writer class in §5.3.2: orchestrator/reaper and outbox workers may append designated non-stream kinds (turn.interrupted, turn.parked/turn.error, title.updated, control acks) under the current epoch without holding the turn lease (e.g. epoch-read-and-stamp in the same transaction), while token/stream kinds stay lease-fenced. Add to S1 acceptance: a turn that parks surfaces a user-visible failure state in the transcript.

### 5. [MAJOR] §2 / 5.1 / 8
**Claim/gap:** The capacity trade for sessions is never named: today a pinned session never waits behind other users at turn time; under pooling with one-turn-per-pod, a burst beyond pod count makes interactive turns QUEUE — with no 'your turn is queued' UX, no queue-position/typing-indicator story, no per-user fairness (round-robin by queued_at is per-unit: one user's 20 parallel sessions can starve another user's single turn), and no p95 TTFT/claim-wait acceptance criterion. §2 sells 'admission, fairness, preemption' for workers; the same mechanism applied to sessions is a silent wait.

**Evidence:** Plausible (design-level, from the doc's own numbers): §8 sizes interactive at warm floor minReplicaCount 1-2 and 'pods sized by concurrent turns' (10 pods : 30-50 sessions); §5.8/§10.3 add gate-parked turns pinning pods if release-at-gate isn't taken; scale-up latency (KEDA-style poll + pod cold start) exceeds a turn's patience. §5.1's fairness bullet addresses only worker batch rotation. Nothing in §9 S1/S2 acceptance measures claim-wait under contention or defines what the composer shows while a turn sits queued.

**Fix:** Add to the design: (a) per-user or per-thread fairness dimension in claim ordering for session_turn (and state whether bg_task units share the interactive deployment's claim loop — if yes, priority policy so cloud pushes never delay turns); (b) a queued-turn client state (the accept-time 200 + turn-request row make 'queued, position N / waiting for capacity' cheap to surface via the journal or /input response); (c) S1 acceptance gains a loaded-bench criterion: p95 claim-to-first-token under 2× pod-count concurrent turns, and a stated policy for what users see when the deployment is saturated.

### 6. [MAJOR] §7 (deletion ledger) / 5.3.6
**Claim/gap:** Deleting the live-settings mutation ladder in favor of 'write override, next turn resolves fresh' silently regresses mid-turn settings semantics: today a permission-mode change applies to the very next tool call INSIDE the running turn and immediately sweeps pending approval cards; under the stateless model a user who downgrades to a stricter mode while watching a turn run (the exact moment users reach for that control) gets no effect until the next claim.

**Evidence:** Verified: src/api/persistent_app.py:3099 mode.set assigns _session.permission_mode in-process; the gate decision re-reads it per tool call at :4625 and :4903, so a mid-turn change bites on the next tool; :5029 documents the concurrent mode.set sweep of the blocked permission row. §5.3.6 fixes only the persistence half ('persist to the thread row'); §7 explicitly states settings become next-turn ('write override, next turn resolves fresh'). Nothing says the turn executor re-reads mode mid-turn.

**Fix:** Specify that the turn executor re-reads permission/narration mode from the thread row at each gate decision (one indexed read per tool call, or piggyback on the 20 s lease renewal RETURNING like worker steering in §5.2/§5.4.3), and keep the mode-downgrade sweep of pending permission rows working cross-pod. Name any remaining latency (≤ renewal interval) explicitly as an accepted change.

### 7. [MAJOR] §10.3 / 5.3.6
**Claim/gap:** Release-lease-at-gate has no user-facing story: today approval → tool execution is near-instant (in-process LISTEN/NOTIFY waiter); under lean-release it becomes approval → enqueue → claim (poll jitter + possible capacity wait) → cold re-hydration (~0.3-1 s S2) → re-execution, PLUS a full epoch cascade whenever the resuming claim lands on a different pod — i.e. in supervised mode (approval on every write tool) the most approval-heavy users eat the cascade most often. Card re-announce behavior on the resumed claim ('re-announcing restored tool_call_ids') is asserted as supported but never specified from the user's side (does the already-approved card re-render? does a second pending card appear?).

**Evidence:** Verified chain from the doc's own text: §10.3 leans release; §5.3.2's epoch bumps on writer change; a gate-resume on another pod is a writer change; cascade cost verified at persistent-chat.service.ts:1628-1680. Today's instant path verified via research code_session-residue.md §9 (DB rows + trigger + NOTIFY, waiter wakes in-process). No approval-to-resume latency target exists anywhere in §9.

**Fix:** If release-at-gate is chosen, add: (1) route-back affinity for gate resumes (prefer last_pod strongly; treat gate-resume-on-same-pod as the common case to avoid the cascade); (2) an approval-to-visible-resume latency target in S2 acceptance (e.g. p95 < 3 s); (3) a one-paragraph spec of card behavior across release/resume (row id stable, card never duplicates, approved card shows 'resuming…' state).

### 8. [MINOR] §10.5 / 5.3.6 / 9-S1
**Claim/gap:** 'Images-visible-one-turn' is offered as an acceptable S1 decision without naming it as a product regression or requiring UI messaging: a user who uploads a screenshot and asks a follow-up gets a model that silently cannot see the image, every session, with nothing in the UI saying so. Today this bites only on rare resumes; per-turn reload makes it the steady state.

**Evidence:** Verified via research code_session-residue.md (surprises): _serialize_message_row flattens list content — image blocks dropped at write; restore projection excludes them. The composer ships image upload as a first-class feature (multimodal PDF/image paths exist per repo memory). §9 S1 lists 'message-fidelity decision' as a build item but the acceptance criteria contain no media-visibility test either way.

**Fix:** Make the S1 acceptance explicit in both branches: either 'uploaded media visible to the model on turn N+1' (structured-content storage lands with S1), or the degraded option ships WITH a visible UI notice on media past their turn ('no longer visible to the assistant') — silent degradation should not be an option.

### 9. [MINOR] §5.3.3 / 7
**Claim/gap:** The officer boot-wake fix is mis-keyed: 'must key on lease-generation change' would still inject a synthetic wake (an LLM turn + a visible transcript event) on every cross-pod re-claim — over-waking officers under load — when under stateless the wake's reason to exist (a parked in-process loop that would otherwise never start) disappears entirely: sleep is 'no lease + durable timer that enqueues a turn request'. No user-visible change during migration (officers keep dedicated pods per §7), but the stated future fix is wrong.

**Evidence:** Verified: src/api/persistent_app.py:2244-2259 — the wake exists because 'the loop starts LAZILY … a freshly booted or respawned officer would otherwise park forever'; its dedup guard keys on in-process _loop_task state (exactly what statelessness deletes), and the comment records a k3d duplicate-wake incident as the failure mode to avoid. §4.8/§7 already establish the durable-timer sleep model that makes the wake redundant.

**Fix:** Change §5.3.3's parenthetical: for stateless officers, delete the boot wake (the durable orchestrator timer is the bootstrap); if any wake survives, key it on cold session start/explicit resume — never on lease-generation change.

### 10. [MINOR] §5.3.1 / 5.3.5 / 10.7 / 2-vs-9
**Claim/gap:** Small preserved-signal and consistency gaps: (a) the /input response's queue_depth field is computed from the in-process asyncio queue and must be recomputed from turn-request rows orchestrator-side — the doc never states /input response parity (cockpit verified not to consume it, so contract-level only); (b) canvas co-editing presence (in-process 15-60 s TTL leases) dies at every lease release until Q7 resolves — presence flicker between turns is a user-visible S2 regression not named in S2 acceptance, only in an open question; (c) §2 claims create-to-first-token 'sub-second' while §9 S1 accepts '< 2 s' — pick one number.

**Evidence:** Verified: src/api/persistent_app.py:2851 `"queue_depth": _loop_user_queue.qsize()`; grep of cockpit/src/app finds no queue_depth consumer (draft-title handling is explicitly loss-tolerant by design, :217 comment — no issue there). Canvas presence in-process TTL leases verified via research code_session-residue.md §1. The sub-second (§2) vs <2 s (§9) discrepancy is on the face of the doc.

**Fix:** (a) Add one line to §5.3.1: /input response contract (including queue_depth) is preserved, computed from unconsumed turn-request rows. (b) Add 'canvas presence continuity across turn boundaries (no flicker between consecutive turns on the same thread)' to S2 acceptance or explicitly accept and name the flicker. (c) Align §2's headline number with the S1 acceptance criterion.
