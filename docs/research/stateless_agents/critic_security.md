# critic-1

## verdict
Technically deep and well-researched on correctness (lease/fence/epoch/journal/replay), but the doc has a systematic blind spot on the exact security consequence it introduces: any-pod-can-claim-any-thread. There is no threat-model or blast-radius section for the tenancy inversion, and three concrete gaps follow from that omission. (1) CRITICAL: the pull-claim credential path is unauthenticated per-tenant and the section-5.6 claim that \"the claiming pod re-runs the resolution pipeline\" is a category error — credential resolution is orchestrator-side and Vault-backed, the stored jobs.resolved_config is redacted, and the only pod auth is a single shared MCP_INTERNAL_KEY, so a single compromised pod goes from holding one job's creds to serially harvesting every tenant's creds. (2) MAJOR: process-global credential residue (the EMBEDDING_API_KEY os.environ swap is written but never popped, and its singleton is reset only conditionally) is dismissed as an S4 concurrency concern when it is a v1 sequential cross-tenant leak on a warm pod; the doc's own KB-embedding path was hardened pop-first for exactly this reason but the memory path was not. (3) MAJOR: the fencing machinery is presented as the safety story yet is only a correctness/anti-zombie boundary among cooperating honest pods — a compromised pod ignores it, most tables are unfenced, and reads are never gated, so real isolation still rests on the broad shared DB role + shared SSH/internal keys, which statelessness does not tighten and arguably widens. None of these block the idea, but each changes the design (keep credential delivery orchestrator-mediated even under pull; a scrub-on-claim requirement with an acceptance test; an explicit threat model) and belongs in S1/S3 scope, not deferred to S4. Two minor items (revocation is next-claim not mid-batch; session-JWT deletion must be gated on P6) round out the security lens.

## findings (5)

### 1. [CRITICAL] §5.6 (also 4.3, 9/S3)
**Claim/gap:** "The claim carries ids, never secrets. The claiming pod re-runs the existing resolution pipeline (_inject_dispatch_credentials + grant PEP + datasource re-authorization)." For the worker lane the doc wants pull-shaped claiming, but never says what authenticates a pod's right to claim a given tenant's unit or to fetch that unit's resolved credentials. The trust inversion (pod pulls creds instead of orchestrator pushing to a pod it selected) is unaddressed, and the sentence is a category error: the pod cannot re-run that pipeline.

**Evidence:** VERIFIED. The resolution pipeline is entirely orchestrator-side and Vault/DB-backed: _inject_dispatch_credentials (main.py:3201), _enforce_dispatch_grants + inject_blob_credentials + resolve_api_keys_for_job (main.py:2529, 3230, 3855). The agent process has no DB-backed model/credential resolution — model_registry.py:203-212: "In contexts without a DB (agent process, tests), the hooks stay None." jobs.resolved_config is persisted REDACTED — store_resolved_config(job_id, redact_config_override(resolved_config)) (main.py:3873). So a claiming pod can neither self-resolve nor read secrets from the stored blob; it must fetch freshly-injected creds from the orchestrator. The only pod↔orchestrator auth is a single shared secret trusted iff X-Internal-Key == MCP_INTERNAL_KEY (auth.py:632-633), identical on every pod, zero per-thread scope; the SSH workspace key is likewise a deployment-mounted shared secret. Blast-radius change: today the orchestrator PUSHES one job's creds to one pod it chose; under pull-claim any pod with the shared key can claim tenant after tenant and receive each tenant's LLM keys, datasource creds, repo creds, and per-user embedding keys — one compromised pod becomes a serial cross-tenant credential harvester. The historical audit named the softer version: "the trust boundary at delivery is just ‘we sent it to whoever was registered’" (multi_tenancy.md §Agent↔orchestrator).

**Fix:** Add a threat-model/blast-radius subsection for any-pod-any-thread. Keep credential delivery orchestrator-mediated even under pull: the pod pulls WORK from run_queue, then the orchestrator delivers resolved creds only to the pod proven to hold the current lease_token for that unit (server-side check), or mints a short-lived per-claim credential token bound to (unit_id, lease_token). Correct §5.6 to name the orchestrator as resolver; keep the shared MCP_INTERNAL_KEY as "is-an-agent" proof only, never "entitled-to-this-tenant" proof.

### 2. [MAJOR] §8/point 3 (also 5.3.6, 5.6)
**Claim/gap:** De-globalization is framed purely as an S4 concurrency optimization ("v1 ships one active turn per pod and skips all of it; multiplexing is an S4 density optimization"). This misses that a warm stateless pod serves many tenants' turns SEQUENTIALLY, so process-global credential/tenant state left in memory between claims is a v1 cross-tenant residue leak — which one-turn-per-pod does NOT solve, and the doc's own scrubbing is incomplete.

**Evidence:** VERIFIED. Pods stay warm across tenants (§2 "10 pods serve 30–50 sessions"; §5.8 warm floor) and §8.3 declines to touch the globals for v1. The embedding override writes a per-user secret into process-global os.environ with the singleton reset only conditionally and the memory keys NEVER popped: os.environ["EMBEDDING_API_KEY"] = str(env_keys[k]); _embedding_module._embedding_service = None gated on `if any(k in env_keys for k in memory_embedding_keys)` (persistent_app.py:1972-1988). Contrast apply_kb_embedding_env, deliberately hardened pop-first for pod reuse: "Agent processes can be reused. Clear every known field first so switching ... cannot retain a previous endpoint or credential" (embedding_service.py:441-459). Consequence: a following tenant whose config omits env_keys (falsy _env_keys_src) skips the whole memory-embedding block — os.environ still holds the PRIOR tenant's EMBEDDING_API_KEY and the singleton is not reset, so that tenant's private memory text is embedded via another tenant's endpoint/credential. register_mcp_tools is safe (clears stale mcp entries first, registry.py:261-267) — the embedding path is the hole; guidance inboxes (dual_app.py:254-265) and ToolContext caches are the same residue class.

**Fix:** Add an S1 requirement to scrub all process-global credential/tenant state at every claim (pop EMBEDDING_* and KB_EMBEDDING_ENV_KEYS, null BOTH embedding singletons unconditionally, clear guidance inboxes and ToolContext caches) and extend apply_kb_embedding_env's pop-first discipline to the memory keys. Add an S1 acceptance criterion: after a claim for tenant B on a pod that last served tenant A, no tenant-A secret remains in os.environ and no A-bound singleton/client is reachable. Reframe §8.3: one-turn-per-pod removes the concurrency hazard, not the sequential-residue hazard.

### 3. [MAJOR] §5.2 (also 5.1, 5.3.2)
**Claim/gap:** The lease/fencing machinery is positioned as the safety story for the any-pod-any-thread inversion, but fencing is only a correctness/anti-zombie mechanism among COOPERATING honest pods — not a security or tenant-isolation boundary — and the doc never says so. Its "be honest" note concedes only the workspace-side SSH gap.

**Evidence:** VERIFIED/analytic. The fence is a voluntary check the writing pod runs: "Every persist transaction ... opens with SELECT 1 FROM run_queue WHERE unit_id=$1 AND lease_token=$2 ... FOR SHARE" (§5.2). A compromised pod omits the SELECT and writes with any token; many tables carry no fence (jobs.context steering/guidance, threads metadata, memories/vector, audit), and fencing never gates READS. A compromised pod's blast radius is therefore unchanged by fencing and bounded only by the broad shared agent DB role + shared SSH key + shared MCP_INTERNAL_KEY — none tightened by statelessness. The inversion widens the routine surface: §5.1 has every idle pod directly SELECT/UPDATE run_queue across all tenants every 250 ms–1 s, and dedup_key ('cloud_push:<thread>') enumerates thread ids to every pod.

**Fix:** Add a paragraph distinguishing fencing (defends Postgres state against slow/zombie HONEST pods) from tenant isolation (still DB role + NetworkPolicy, unchanged). State the compromised-pod threat model and give stateless pods a least-privilege DB role for the claim/persist path (or route worker claims through the orchestrator too) instead of broad cross-tenant SELECT/UPDATE on run_queue and the persist tables.

### 4. [MINOR] §5.6 (bonus bullet)
**Claim/gap:** "credential/grant revocation takes effect at batch granularity — an improvement over today's job-lifetime credential validity." True at the next claim, but incomplete: there is no mid-batch revocation path and secrets already materialized into the running pod persist for the whole batch.

**Evidence:** VERIFIED for the next-claim half: _resume_job_on_agent re-runs _enforce_dispatch_grants against current grants and fails closed on revoked rows (main.py:4080-4090). But nothing revokes mid-batch — once a batch loads LLM client headers, os.environ EMBEDDING_API_KEY, and live datasource clients, DB-side revocation does not scrub them, and a batch is 25–50 supersteps / potentially many minutes with long tool calls (§5.4.3, appendix).

**Fix:** State the caveat: revocation is effective at the next claim, not mid-batch; already-materialized secrets remain usable until release. Tie the hard wall-clock batch cap floated in §5.4.3 to this bound, and avoid implying revocation reaches a running pod.

### 5. [MINOR] §7 (Deletion ledger)
**Claim/gap:** "Delete ... 60 s session JWTs (journal SSE + REST input replace the direct WS; P6 finishes this)." Safe only once P6 lands and only if no non-WS consumer remains; the ledger lists it as a delete without crisply gating it, and it removes the one place a client authenticates to a SPECIFIC pod.

**Evidence:** PLAUSIBLE/verified-adjacent. Session JWTs authorize the direct /ws/chat handshake (session_tokens.py:28-73, claims aud=agent). IDE and browser live on the WORKSPACE pod behind the orchestrator BFF proxy (ide_proxy.py) using resolve_ws_user cookie auth, not the session JWT (multi_tenancy.md coverage map) — so their auth is unaffected and the delete is clean IF P6 has retired the chat WS.

**Fix:** Explicitly gate the session-JWT deletion on P6 completion and verify no other consumer of the srw-session-jwt secret remains before removal; keep it minted until P6 soaks. Note that after this delete clients authenticate only to the orchestrator (SSE/REST), never to a specific agent pod — the desired end state, but state it.
