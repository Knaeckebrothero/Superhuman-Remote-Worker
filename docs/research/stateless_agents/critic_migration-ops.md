# critic-5

## verdict
The doc's substrate inventory (§4) is excellent, but its migration story does not survive contact with the code. The three load-bearing coexistence claims all fail: (1) there is no single claim authority for workers during rollout — the run_queue lease and the shipped jobs-row lease coexist on the same job with different renewers and different reapers, and the unpartitioned legacy predicates (get_dispatchable_jobs, recover_expired_lease_jobs, claim_job_for_agent) will re-dispatch a stateless-claimed job to a pinned agent mid-batch; (2) S1's scoping premise "lite sessions (no PVC exists)" is contradicted by the shipped provisioner, which PVC-backs /workspace for ALL sessions precisely because lite sessions hold load-bearing agent-local state; (3) S1 sessions have no transport for most control verbs (mode.set, rewind, compact, config.update, tier upgrade are control-WS-only and P6 is not started), yet the S1 build list omits the migration. Beyond these, §5.5's TTFT mechanism contradicts the 2-replica deployment the doc itself cites, §5.8 asserts a chart shape (two Deployments + KEDA) that reverses a deliberate chart decision and adds an unmentioned cluster-level dependency, the four freeze-type lists hide a rollback path in which loop jobs silently complete with partial work, and the deletion ledger has no delete-when discipline — the honest steady state for the whole soak is dual control planes, an operational tax §2's payoff framing never prices. None of this argues against the direction; all of it argues the §6/§7/§9 sections need a real coexistence design, not a rollback flag.

## findings (10)

### 1. [CRITICAL] §5.4.3/7/9-S3
**Claim/gap:** Pinned and stateless worker classes can coexist behind a per-mode flag; release re-enters via _trigger_dispatch and 'another ready pod claims in seconds'. The doc never defines a single claim authority per job, and the two lease systems (run_queue vs jobs-row) will double-execute jobs during rollout.

**Evidence:** VERIFIED. The shipped jobs-row lease is renewed only by the agent-identity heartbeat (postgres.py:5235-5260, fenced by assigned_agent_id) which a stateless pod doesn't have; the KEPT stale_agent_detector (required for officer/pinned/bare-metal lanes) runs recover_expired_lease_jobs (postgres.py:5504-5538) which unconditionally flips any expired-lease processing job to paused+unassigned; get_dispatchable_jobs (postgres.py:6885-6958) has NO class partition, so the leader dispatcher then offers that job to a pinned agent via claim_job_for_agent while the stateless pod's run_queue lease is still healthy — two executors writing checkpoints to the same thread_id=job_id. §5.4.3 itself mixes the planes (uses _trigger_dispatch + the 30s get_available_agents cooldown, both legacy-push artifacts that don't exist in a pull model). Also unstated: who enqueues worker_batch rows — the kept workspace pre-filter lives in the leader's _try_dispatch_pending_jobs, so the leader dispatcher remains load-bearing as the enqueuer, which changes §5.8's 'dispatch latency is the pods' own poll'.

**Fix:** Add a §on-coexistence: (a) one claim authority per job — partition get_dispatchable_jobs, claim_job_for_agent, and both lease sweeps on a job-class column (jobs.runner_kind already exists and is already SELECTed by the dispatcher); (b) specify that the stateless claim transaction also CASes the jobs row and that run_queue renewal writes jobs.lease_expires_at (or that the legacy sweeps exclude the stateless class); (c) name the leader dispatcher as the post-workspace-preflight enqueuer for worker_batch rows and state the resulting latency path.

### 2. [CRITICAL] §6.1/9-S1
**Claim/gap:** "S1 scopes to lite sessions (no PVC exists)" — S1 is framed as avoiding the session-agent PVC and every workspace dependency.

**Evidence:** VERIFIED FALSE. agent_provisioner.py:330 creates pvc-agent-s-<tid12> for ALL pods with purpose=='session' (no lite carve-out), and the pod-manifest comment (agent_provisioner.py:1448-1462) says explicitly: lite/none sessions 'have no workspace pod at all, so agent-local state written under /workspace is the only copy and it died with every pod recycle... for lite sessions it [the PVC] is the fix.' So lite sessions carry load-bearing agent-local /workspace state today (the very wipe-bug class the doc cites in §2). With pvcEnabled=false (chart default, values.yaml:1501) the state is emptyDir and per-turn pods lose it EVERY turn; with the PVC on (the dev fix), a Deployment can't mount the RWO claim. Either way the S1 premise is wrong. Note: the doc inherited this from the control-plane research report ('for lite sessions (S1) there's nothing to mount'), which the shipped manifest comment contradicts.

**Fix:** Replace the S1 scoping sentence with a work item: inventory what lite sessions write under agent-local /workspace (uploads staging, memory/KB artifacts, canvas-adjacent files), externalize each to the object store/DB or declare it disposable per item, and only then claim S1 avoids the PVC. Until that inventory exists, the PVC prerequisite is S1's, not S2's.

### 3. [MAJOR] §9-S1/7
**Claim/gap:** S1 ships stateless lite sessions while the per-session Service/Ingress + control WS are deleted for that class, with 'P6 finishes this' — but most session control verbs have no non-WS transport and P6 is not started, and S1's build list contains no control-verb migration.

**Evidence:** VERIFIED. persistent-chat.service.ts sends compact (:2758), archive (:2761), undo (:2780), mode.set (:2942), narration.set (:2947), config.update (:2963), rewind (:3000), upgrade-to-workspace (:3064) exclusively via _sendControl → controlWs, whose handshake rides the per-session route to the pinned pod; session_reliability doc status table: P6 'not started', _installControlWs still live. A stateless thread has no pod and no route to socket to. Only permission decisions are REST-first (/threads/{tid}/approve/{approval_id}, service.ts:2853-2878, WS as fallback) and interrupt/input are REST. Consequence: S1's own build item 'persistence promotions (mode.set…)' has no transport to invoke mode.set from, and rewind/compact/config-change/tier-upgrade break silently for stateless sessions.

**Fix:** Add to S1's build list an explicit P6 subset: orchestrator REST routes + journaled acks for mode.set/narration.set, compact, archive/undo, rewind, config.update, upgrade-to-workspace (P6 §6a shape). Alternatively scope S1 to a degraded-controls beta and say so in the acceptance criteria — the doc currently implies full session UX.

### 4. [MAJOR] §5.4.1/9-S3
**Claim/gap:** batch_boundary wiring is 'four keep-in-sync list touches' — presented as a bounded edit, with no consolidation proposal and no deploy-order/rollback constraint. The doc also misses that the unknown-freeze-type default is NOT uniformly pending_review.

**Evidence:** VERIFIED. The four lists exist as described (completion.py:340, completion.py determine_job_status default, postgres.py:5486-5489 SQL literals, agent.py:77-85). But completion.py:~1615-1626 maps an unknown freeze type on a LOOP job to ('completed', None) — 'mapping to completed so the loop advances' — before the pending_review fallback. So an agent-first rollout, or an orchestrator rollback during the S3 soak, turns every mid-batch batch_boundary on a loop job into a phantom-COMPLETED job whose partial work the RSI loop merges; non-loop jobs mass-park in pending_review. The lists span two images that Fleet rolls together, so skew windows are guaranteed.

**Fix:** State the hard constraint: orchestrator (all replicas) must understand batch_boundary before any agent image emits it, and orchestrator rollback during soak requires disabling batch mode first. Propose consolidating the freeze-type registry into one shared constants module (src/shared/ — the orch_surface move this week is the precedent) consumed by agent + completion.py, and parameterize the recover_orphaned_jobs SQL literal list from it.

### 5. [MAJOR] §5.5/5.2
**Claim/gap:** 'Pin the SSE poll at 200 ms while a turn is in-flight — the orchestrator receives the input POST — it can wake its own pollers; no NOTIFY infra needed', and §5.2's reaper justification 'the orchestrator is already the elected singleton'. Both misstate the 2-replica deployment.

**Evidence:** VERIFIED. helm/values.yaml:123-127 defaults orchestrator replicas: 2; no sessionAffinity/sticky annotations exist on the orchestrator service/ingress templates. The client's SSE stream and the input POST land on independent replicas, so the in-process wake misses whenever they differ — TTFT keeps the 1 s idle-backoff penalty the S1 '<2 s create-to-first-token' acceptance budgets away. The doc knows about the replicas (§2 calls the 'Single-instance orchestrator' comment stale) — an internal contradiction. And leader election is per-loop with a documented dual-leader window requiring CAS guards on every side effect (leader_election.py:180-184; bench-sweeper race is the in-repo proof) — 'already the elected singleton' is not the architecture.

**Fix:** Replace the wake mechanism with the P5 thread.activity DB trigger → pg_notify fan-out the doc itself blesses in §6.4 (or accept cross-replica misses and say the TTFT criterion holds only via the 200 ms floor). Add a replica-safety table for every new component: enqueue (any replica), reaper (leader-gated loop whose steal UPDATE must be — and is — CAS-safe under dual-leader), outbox consumers (pods), prune sweepers (leader).

### 6. [MAJOR] §5.8
**Claim/gap:** 'Deployment shape — question closed: one image, exactly two Deployments, KEDA postgresql scaler' — asserted with no chart, values, dependency, or local-dev content.

**Evidence:** VERIFIED gaps: (a) the chart has NO agent Deployment today — deliberately removed ('The static Deployment was removed in Phase 1a… agent.replicas is no longer honored', helm/values.yaml:344-349); the agent Service/PDB select provisioner pods via shared chart labels, so new Deployment pods must use distinct labels or the KEPT reap_pods (label-selector list at agent_provisioner.py:842-846) and PDB counts entangle both classes during coexistence; (b) KEDA appears nowhere in helm/ or the Tiltfile — it is a new cluster-level operator for prod (Fleet), homelab, and k3d bootstrap, and the postgresql scaler needs a TriggerAuthentication + DB connection secret through Vault/ESO; (c) Tilt's agent inner loop is 'rebuild image → orchestrator provisions the NEXT pod with the new tag' (Tiltfile:170-179) and must be rewired for static Deployments.

**Fix:** Reopen the question enough to add: the values/flags sketch (interactive.replicas/minReplicaCount, worker ScaledObject + trigger auth), the class-partitioning label scheme, KEDA as a named new dependency with its k3d/Fleet install step, and one paragraph on the Tilt story (live_update against the Deployments — likely an improvement worth claiming).

### 7. [MAJOR] §7
**Claim/gap:** The deletion ledger conflates per-class dead code with shared infrastructure and has no 'delete when' column — the actual steady state for the entire migration is dual control planes, an ongoing operational tax §2's 'gets deleted' payoff never prices.

**Evidence:** REASONED from verified facts: registration endpoint, agents table, heartbeat, stale-agent sweeps, warm pool are listed under Delete, but the doc's own keep-lanes depend on all of them — officers have no retirement plan ('migrate last… later'), bare-metal/compose (agent.py --loop) is still a documented deploy target (CLAUDE.md), and the pinned rollback path must survive the full soak. Table-level artifacts (agents, registration, heartbeat endpoint) cannot be deleted 'for the stateless class'; they are deleted only when the LAST lane migrates. Meanwhile every dispatch/sweep/provisioning predicate becomes class-aware (see finding 1), and the §2 reliability-graveyard claims (detector class disappears, drain machinery deleted) are deferred until officer + bare-metal retirement — dates the doc doesn't have.

**Fix:** Add a third ledger column: delete-when (S1-flag-flip / after-officer-migration / after-bare-metal-decision / after-P6), plus an explicit decision request: does bare-metal remain supported (if yes, either it also runs the stateless executor as plain polling processes, or registration is permanent)? Price the dual-plane period in §9 as its own operational cost, not a footnote of 'rollback at every stage'.

### 8. [MAJOR] §5.2/9-S1
**Claim/gap:** The fencing-boundary paragraph scopes the residual zombie window to 'in-flight SSH/tmux side effects on the workspace pod' and defers the closer (workspace-side executed-calls dedup) — but S1's lite tier has durable side effects with NO possible workspace-side dedup home, and non-atomic writes.

**Evidence:** VERIFIED. src/core/backends/virtual.py header: 'append_file/edit are read-modify-write with no atomicity — safe under the tier's single-writer-per-prefix assumption.' Under S1, a zombie pod's in-flight edit against the object store during the ≈grace+one-tool-call window violates exactly that single-writer assumption while the successor writes the same prefix — lost updates or interleaved corruption in the user's durable files. The promised v2 idempotency layer is 'workspace-side' dedup, and lite tiers have no workspace pod to host it. S1's acceptance criteria (pod deleted mid-turn → clean steal) never test concurrent object-store writes.

**Fix:** Either add object-store write fencing to S1 (fence-check the run_queue token immediately before each object PUT, or a per-prefix generation stamp in object metadata), or explicitly accept and document the lite-tier corruption window with its size — and add a mid-turn-steal-with-writes case to the S1 acceptance list.

### 9. [MINOR] §5.2/5.3.2
**Claim/gap:** The generic claim SQL bumps lease_token on EVERY claim (lease_token=lease_token+1), while §5.3.2 requires the session token — which §5.2 says 'should *be* threads.events_epoch' — to bump only on writer-identity change. Both statements cannot hold for sessions; the reconciliation and the fenced-table set are left implicit.

**Evidence:** REASONED from the doc's own text: §5.2 claim statement (unconditional bump, attempt+1, backoff keyed to it) vs §5.3.2 CASE-bump-on-writer-change. The no-bump-on-same-pod variant is sound only because the persist fence also checks state='leased'; that dependency is never stated. Corollary: §5.3.5's 'pod finishes background work after releasing the lease' means post-release persists to any fenced table abort by construction — safe only because memory/citation writes land in unfenced stores (vector DB, object store), which the doc also never states.

**Fix:** Show the session-variant claim SQL explicitly (CASE bump + state check), note the double-bump-per-steal consequence, and add one sentence enumerating fenced tables (thread_messages, thread_events, checkpoints, job transitions) vs deliberately unfenced stores that post-release background work may touch.

### 10. [MINOR] §6.4/9
**Claim/gap:** 'Epoch-stability lands before P5' is asserted as sequencing, but nothing enforces it: the constraint lives only in this doc, not in session_reliability (whose P5 it constrains), and both changes edit the same SSE loop.

**Evidence:** VERIFIED context: session_reliability_and_transport_simplification.md is PARTIALLY SHIPPED with P5 'not started' and its own momentum/backlog entry; both P5 (idle-close, /events/head, activity trigger) and the epoch redesign modify orchestrator/main.py:30489-30778. A P5 implementer working from the reliability doc alone would land idle-close first — which the stateless doc itself admits converts the 2.2 s cascade into an at-open full reload per turn rather than fixing it.

**Fix:** Record the dependency in the session_reliability doc's P5 section (one line: 'blocked-by: stateless_agents §5.3.2 epoch-stability') and state the compatible-order fallback: if P5 lands first, the epoch change must ship before any stateless session serves traffic, with the /events/head contract kept stable across both.
