# critic-0

## verdict
The doc is excellent where the research fan-out looked — lease/fence mechanics, session residue, batch seams, streaming — but its system boundary is drawn at "executor + store," and everything that consumes agent *identity* from the outside fell off the map. The deletion ledger (§7) deletes the agents table and orchestrator-driven pod deletion without noticing three verified dependents: the infrastructure-metering agent_pod attribution lane (billing becomes "shared platform capacity" for the whole stateless class), the job-log S3 archive (whose sole trigger is delete_agent_pod and whose job attribution resolves through the agents table), and the admin/MCP/cockpit agent surface. Equally missing is the entire *admission* side of the new queue: the doc specifies claim/steal/release exhaustively but never says who enqueues — job creation after workspace pre-flight, automation cron fires, delegation merge (waiting→paused), blocking_message reply resume, approval, backoff sweepers — nor the jobs.status↔run_queue consistency contract, and §5.4.3 still narrates release in today's push-dispatch vocabulary. Finally, the acceptance criteria lag the failure modes §5 itself introduces: the persist-time fence and the parked state are never tested or surfaced, and S2 — which the doc calls its hardest inventory — ships with no acceptance criteria at all. None of this invalidates the direction; all of it would change §5/§7/§9 before implementation starts.

## findings (8)

### 1. [CRITICAL] §5.1/5.4.3/9-S3
**Claim/gap:** The queue's producer/wake surface is entirely unspecified, and worker admission is internally ambiguous. §5.1 defines run_queue and the claim; §5.4.3 describes release as today's push flow ("release → paused ... → _trigger_dispatch() fires; another ready pod claims") while §9-S3 says "pull-claim" — but nothing states who INSERTs run_queue rows or when: job creation after the kept workspace pre-flight (VM_PROVISION/VM_WAIT parks), automation cron fires, delegation merge, blocking_message reply, sudo/review approval, resume_job_with_feedback, the llm_unavailable backoff sweeper, or what happens to a queued/leased row on user pause/cancel/priority change. jobs.status and run_queue.state become two sources of truth for runnability with no consistency contract.

**Evidence:** Verified: orchestrator/services/cron_dispatcher.py:1-60,209-213 (automations create jobs then nudge _trigger_dispatch — a producer the doc never routes); orchestrator/database/postgres.py:5979-6014 (claim_delegation_resume: waiting→paused CAS + freeze clear, exists precisely because re-queue-on-wake needs its own CAS — a second claim path the run_queue design must absorb); orchestrator/main.py:12510-12525 (_route_inbound_reply → _internal_resume_job for waiting_for_reply — reply-wake producer); doc §5.4 covers only the batch_boundary self-release path.

**Fix:** Add a "queue admission and wake" subsection to §5.4: enumerate every producer (create-after-pre-flight, automation fire, delegation merge, reply wake, approval, feedback resume, backoff re-queue) and state the single rule that maps jobs.status transitions to run_queue rows (e.g., run_queue row exists iff status ∈ {created-ready, paused}; waiting/waiting_for_reply/pending_review have no row; every existing wake path ends in one shared enqueue helper instead of _trigger_dispatch). Specify queued-row disposition on pause/cancel/preempt. Rewrite §5.4.3's release sentence in pull vocabulary.

### 2. [MAJOR] §7
**Claim/gap:** Billing/metering is never mentioned, yet the shipped infrastructure-metering agent_pod lane attributes compute strictly through the identity §7 deletes: attribution is accepted only when Pod UID + name resolve to a DB-converged agent row with a mutual job/thread binding; an unbound worker is explicitly "shared platform capacity". Deleting registration + the agents table makes every stateless pod permanently unattributable — customer compute attribution for the agent tier silently degrades, defeating an active investment (migrations 0103-0114).

**Evidence:** Verified: orchestrator/services/infrastructure_metering/agent_intervals.py:1-14 (attribution contract quoted above; AgentPodIntervalReconciler mutates agent_pod lifecycles), config.py:143-145 (agent_pod_shadow/publication flags), migrations 0103_compute_metering_foundations.sql … 0114_compute_interval_epoch_shape_repair.sql.

**Fix:** Add a metering row to §7 and a work item to §9: attribution moves from pod-identity to lease intervals — run_queue leases already yield exact (unit_id, leased_by, claim_at, release_at) spans, a strictly better attribution source; the AgentPodIntervalReconciler needs a lease-interval ingestion path and a cutover flag before the stateless class carries paying traffic. While editing §5.3.5, also add the turn-end llm_requests archive task to the re-homed background-work list (it is absent alongside memory capture/title gen).

### 3. [MAJOR] §7
**Claim/gap:** §7 keeps the "job-log S3 archive (already keyed by job — the per-turn observability substrate)" while deleting the machinery that makes it fire and attribute: the archive's only trigger is orchestrator-driven pod deletion, and job stamping resolves through the agents table. For a Deployment-managed stateless class the orchestrator never deletes pods (ReplicaSet does), so the archive never fires; and stamping matches only currently-assigned jobs, so a pod that served 50 batches would attribute at most its last. Per-job log observability (get_job_logs archive fallback, MCP get_job_log) silently dies for the stateless class.

**Evidence:** Verified: orchestrator/services/agent_provisioner.py:432-437 ("the one choke point all deletion paths share" — _archive_pod_logs inside delete_agent_pod), :565-583 (stamp via `assigned_agent_id IN (SELECT id FROM agents WHERE hostname=$1)`; comment: the job→pod link "dies with the agent row"), orchestrator/main.py:32505-32530 (get_job_logs falls back to log_archive_keys). §7 simultaneously deletes reap_pods ("normal ReplicaSet semantics").

**Fix:** Replace the §7 "keep" with a redesign item: per-claim log capture — e.g., the executor writes unit-scoped logs (or ships the correlation-tagged slice) to S3 at lease release, or a preStop hook uploads the pod log with unit-id stamping derived from run_queue lease history instead of the agents table. Add "job logs retrievable after N batches across M pods" to S3 acceptance.

### 4. [MAJOR] §7/5.8
**Claim/gap:** "The VM lane is a workspace lane, not an agent lane … survives untouched" ignores that reaching a VM workspace is itself agent-pod infrastructure: agent pods carry a Tailscale sidecar ("mesh VPN to KubeVirt VMs") with a darkness liveness probe and a tunnel_dark reaper. Under two generic Deployments, either every replica joins the headscale mesh (KEDA scale-to-zero churns mesh node registrations; a dark tunnel kills the pod and thus any claim it holds) or VM-backed units are claimable only by mesh-enabled pods — and §5.1's claim has no capability dimension (§5.8 concedes only a browser-stack resource split).

**Evidence:** Verified: helm/values.yaml:407-414 (agent.tailscale sidecar "for mesh VPN to KubeVirt VMs", darkTimeoutSeconds comment: liveness kills the sidecar and "the tunnel_dark reaper recycles the pod"); control-plane report: tunnel_dark is a reap_pods category §7 deletes. Operational consequences (mesh churn at scale-to-zero, claim-eligibility flap) are plausible, not measured; mesh fragility precedent: the headscale-latch outage.

**Fix:** Add a claim-eligibility/capability note to §5.1 (unit carries required capabilities, e.g. vm-mesh; pods advertise theirs — or VM-backed units get their own unit_kind served by a mesh-enabled Deployment variant), and correct §7: the VM lane keeps a per-pod mesh dependency; decide sidecar-on-all vs. a third pod class in §5.8, and keep (re-home) the tunnel-dark health signal for whichever class serves VM units.

### 5. [MAJOR] §9
**Claim/gap:** Acceptance criteria do not cover the failure modes §5 introduces, and S2 has none at all. The persist-time fence (§5.2's central novel mechanism) has no test anywhere — S1 tests steal-after-kill but never "zombie's late persist is rejected / no interleaved histories"; S3's gate is a perf/parity A/B with no mid-batch kill/steal case and no test of the stage-4 completion CAS it builds; the 'parked' state has no acceptance criterion and no operator surface anywhere in the doc (no endpoint, alert, UI, or unpark flow — max-attempts units silently leave the queue with "human attention" promised and no mechanism named); S2 — which §5.3.5 calls the hardest inventory (resident daemons, cloud-push fence = data-corruption class) — is a bare build list.

**Evidence:** Verified by doc text: §9 S1 criteria list (steal ≤~90 s, cache, FIFO, zero in-process claim state — no fence-rejection assertion); §9 S2 ("SSH affinity + tmux reattach; …" — no acceptance line); §9 S3 gate ("completion parity, tokens/wall, overhead, KV-cache" — no fault injection); §5.2 'parked' appears twice and never again.

**Fix:** Add: S1 — "pod paused mid-turn past TTL, resumed after steal: its persists abort at the fence, journal writer terminal-fails loudly, no interleaved thread_messages"; S3 — kill -9 mid-batch and steal-during-tool-call cases with completion parity, plus "fenced-out /complete rejected"; define the parked operator surface (listing endpoint + cockpit badge + alert + requeue verb) and an S1 criterion "parked unit visible and unparkable"; give S2 criteria: mid-idle rclone token expiry heals on next claim, push(N)→pull(N+1) ordering holds across a forced pod handoff, tmux state survives handoff.

### 6. [MAJOR] §5.3.5/5.1
**Claim/gap:** The collapsible-task dedup as specified silently drops the push signal while a push is in flight: idx_run_queue_dedup is unique over state IN ('queued','leased'), so when turn N+1 commits while cloud_push(N) is leased mid-walk, the outbox insert conflicts and is lost — breaking §5.3.5's own invariant "turn committed ⟺ follow-up enqueued". The in-flight push may already have walked past N+1's changed files, so the user's cloud copy goes silently stale until some later turn re-enqueues — the same silent-staleness class the 08-06 fix closed.

**Evidence:** Verified from doc text (§5.1 index predicate; §5.3.5 outbox biconditional + "repeated turn-ends collapse to one pending push") plus SQL semantics; the 'leased' term in the dedup scope came from the web report's sketch (web_pg-queue-lease.md, ON CONFLICT DO NOTHING) and was adopted without the lost-refresh analysis. Companion context: docs/done/session_turn_end_cloud_push_blocks_queued_input.md.

**Fix:** Scope dedup to state='queued' only, and make the per-mount ordering fence (sync-generation counter) mandatory rather than "either/or" — two pushes may then coexist (one leased, one queued) and the generation check serializes them; alternatively keep the wide dedup but ON CONFLICT bump a generation/dirty column that the leased worker must re-check before completing, re-queueing itself if it advanced.

### 7. [MINOR] §7/5.3.6
**Claim/gap:** Deleting the agents table orphans a named operator surface the doc never inventories: the cockpit agents admin view (AgentStatus badges over the agents API), the MCP tools list_agents / get_agent_stats / get_agent_system_info / deregister_agent, and assign_job (manual job→agent assignment — its semantics simply vanish with no successor verb). §5.3.6's single line covers only the heartbeat metrics payload, not the enumeration surface; "what pods exist and what are they doing" needs a named replacement (a leases/queue read model) or these go dark at cutover.

**Evidence:** Verified: cockpit/src/app/views/agents/agent-list.component.ts (Agent/AgentStatus consumer); MCP server exposes list_agents/get_agent_stats/get_agent_system_info/deregister_agent/assign_job (live tool roster); §7 deletes the table for the stateless class with no replacement row for this surface.

**Fix:** Add to §7 a "replaced by" entry: a run_queue/lease read model (active leases with unit, pod, age, renewal health) backing the cockpit fleet view and a successor MCP tool set; explicitly deprecate assign_job for the stateless class (or redefine it as a priority/affinity hint), and fold this into the migration-flag story so admin pages don't break while both classes coexist.
