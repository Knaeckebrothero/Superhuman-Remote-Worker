# Migration lint warnings ship to dev because deploy doesn't wait for them

**Status:** Open — partial mitigation in place per incident (offending file added to
`.squawk.toml:excluded_paths`), full fix awaits branch protection per
[docs/branch_protection_setup.md](../branch_protection_setup.md). Two incidents
so far; both followed the same arc.

## Symptom

A migration with squawk findings lands on the dev DB before the lint verdict is
known. By the time `db-migrations.yml` reports ❌, the orchestrator pod has
already rolled out the new image, applied the migration, and recorded its
checksum in `schema_migrations`. From that point on, **editing the file in
place trips the migration runner's checksum guard on the next deploy**, so the
sensible-looking fix ("just rewrite the SQL with NOT VALID / CONCURRENTLY /
IDENTITY") would crash-loop the next orchestrator pod.

The pragmatic option left is to add the file to `excluded_paths` in
`.squawk.toml` and rely on the underlying guidance in
[docs/db_migration.md](../db_migration.md) to keep new migrations clean. The
exclusion is permanent — `excluded_paths` doesn't shrink — so every incident
adds one more line to a list that, at scale, devalues the lint itself.

## Incident history

### 2026-05-12 — BIGSERIAL primary keys (0004, 0006)

`0004_thread_events.sql` and `0006_headless_notifications.sql` shipped using
`BIGSERIAL`, which squawk flagged via `prefer-identity`. Both were applied
to dev before the warning was reviewed. Attempting an in-place rewrite to
`BIGINT GENERATED BY DEFAULT AS IDENTITY` tripped the checksum guard and
crash-looped the new orchestrator pod on 2026-05-13. Recovered by:

1. Reverting the in-place rewrite (kept the BIGSERIAL definitions).
2. Adding `0004` and `0006` to `excluded_paths`.
3. Shipping `0007_thread_pk_identity.sql` as a forward conversion migration.

### 2026-05-13 / 2026-05-14 — Missing NOT VALID + CONCURRENTLY (0008)

`0008_thread_awaiting_user.sql` (Phase 5 of headless persistent sessions)
shipped with two squawk findings:

```
warning[constraint-missing-not-valid]
  orchestrator/database/migrations/app/0008_thread_awaiting_user.sql:43:5
  ADD CONSTRAINT valid_thread_status CHECK (...)

warning[require-concurrent-index-creation]
  orchestrator/database/migrations/app/0008_thread_awaiting_user.sql:70:1
  CREATE INDEX IF NOT EXISTS idx_threads_awaiting_user_since ...
```

Same arc:

| Step | Time (UTC) |
|---|---|
| Commit `0e5994e` pushed to `develop` | 2026-05-13 ~15:30 |
| `develop.yml` (build/test/deploy) ✓ | 2026-05-13 ~15:45 |
| Orchestrator pod rolled out, 0008 applied (success=t) | 2026-05-13 15:47:53 |
| `db-migrations.yml` (squawk) ❌ reported back | 2026-05-13 ~15:55 |
| `0008` added to `excluded_paths` | 2026-05-14 |

Same outcome as the BIGSERIAL incident: one more line in `excluded_paths`,
no forward migration shipped (the warnings are about *initial-application
lock duration* — water under the bridge once the migration has run).

## Root cause

Two contributing factors:

1. **Parallel, independent CI workflows.** `db-migrations.yml` and
   `develop.yml` are triggered by the same push but run as separate workflow
   runs. Failure in one doesn't block the other. `develop.yml` runs build →
   test → deploy as soon as its own gates pass. There is no required-checks
   relationship enforced at the GitHub level.

2. **No branch protection on `develop`.** Direct `git push origin develop`
   is currently allowed. Even if `db-migrations.yml` were structured as a
   required check, GitHub branch protection only enforces required checks on
   PRs (and on pushes if a ruleset is configured) — without protection, the
   direct push lands and triggers the deploy regardless. This is the failure
   mode that [docs/branch_protection_setup.md](../branch_protection_setup.md)
   was specifically written to address.

## Impact

- **Per-incident workaround cost is low**: one line in `.squawk.toml`,
  ~15 minutes of investigation. But the cost compounds:
- **`excluded_paths` accumulates monotonically**. After 2 incidents it covers
  5 files (the cutover snapshots are categorically separate; the post-cutover
  exclusions are 0004 / 0006 / 0008). Each addition slightly weakens the
  signal of "squawk found something" because a non-trivial fraction of
  migrations are now exempt.
- **The lint becomes advisory rather than authoritative.** Developers learn
  that squawk findings can be deferred-then-excluded rather than fixed,
  which is the opposite of what the lint is meant to teach.
- **Some warnings can't be acted on after the fact** even with a forward
  migration. BIGSERIAL was fixable forward via 0007. The 0008 warnings
  (`constraint-missing-not-valid`, `require-concurrent-index-creation`)
  describe *lock duration during initial application* — that event is in
  the past and a forward migration can't retroactively shorten it. So
  `excluded_paths` is the only available remediation for that class.
- **No user-facing impact**: dev cluster has effectively no rows in `threads`,
  no concurrent writers, no SLO. The locks the warnings flag would have
  caused negligible disruption even if uncaught. The cost is procedural,
  not operational.

## Fix

### Phase 1 (recommended, ~15min of GitHub config)

Implement Phase 1 of [docs/branch_protection_setup.md](../branch_protection_setup.md):

- Block direct pushes to `develop`.
- Require `lint`, `dependency-audit`, `codeql (python)`,
  `codeql (javascript-typescript)` from `develop.yml` to pass before a PR
  can merge.

This alone doesn't close the loophole — `db-migrations.yml` is still
path-conditional (only runs when migration files change) and therefore
**not safe to require directly**. But Phase 1 forces every change through a
PR, which means the squawk verdict is at least *visible* on the PR page
before the merge button is clicked. Solo-dev workflow stays cheap: branch +
push + `gh pr create --fill` + `gh pr merge --squash --auto`.

### Phase 2 (closes the loophole, ~1h of workflow refactor)

Implement Phase 2 of the same runbook:

- Restructure `db-migrations.yml` so jobs short-circuit when no migration
  files changed (rather than the whole workflow being path-filtered out).
- Add an aggregator job (`db-migrations / status`) that always runs and
  succeeds iff every individual migration job succeeded or was correctly
  skipped.
- Add `db-migrations / status` to the required checks list.

With Phase 2 in place, a PR that adds a migration with squawk findings
gets ❌ on `db-migrations / status`, branch protection blocks the merge,
no image gets built, and the migration never reaches the runner. The
checksum-lock trap becomes unreachable.

### Workaround (current state)

When a migration with squawk findings has already been applied:

1. **Do not rewrite the file in place** — the checksum guard will trip
   on the next deploy.
2. Add the filename to `excluded_paths` in `.squawk.toml` with a comment
   line documenting which findings it bypasses and when it shipped.
3. If the underlying defect is fixable forward (e.g. type change like
   BIGSERIAL → IDENTITY), ship a numbered follow-up migration. If it's
   about lock duration during initial application, accept that the harm
   is already done and skip the forward migration.
